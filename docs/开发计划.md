### 2.3 `compositive_overview` 重合子类型处理方案（已定，已落地）

`compositive_overview`（综合态势总览）6 个子类型中，4 个与已开发模块高度重合，若独立建意图会导致语义中心向量互相竞争。处理方案：

| overview 子类型 | 处理方式 |
| --- | --- |
| `people_vehicle_num`（在园人数/车位） | 问法继续路由到 `person_status`（realtime/count）与 `vehicle_status`（parking_space），复用现有工具 |
| `energy_consumption`（电/水当日值） | 路由到 `energy_status`（overall_energy/realtime_electricity/realtime_water） |
| `today_meet`（今日会议统计） | 路由到 `meeting_status`（meeting_statistics/meeting_room_status） |
| `security_index`（综合安全指数） | 路由到 `security_status`（security_index） |
| `basic_info`（园区面积、IoT 设备总数） | **新建**：`compositive_overview` 仅保留此独占子类型 |
| `device_health`（总览设备健康度） | **新建**：`compositive_overview` 保留（注意与 `device_status.category_health` 语料区分：overview 只写"设备健康度/健康分"总览问法） |

落地约定：
- `compositive_overview` 模块只建 `basic_info`、`device_health` 两个子类型，走 `/overview/*` 自己的接口（`getBasicInfo`、`getDeviceHealth`）。
- 语料严禁收录"多少人/能耗/会议/安全指数"类问法，避免与其他意图中心向量贴近。
- 开发量从 6 个子类型降为 2 个。

### 2.4 `emergency_aialert` 并入 `security_status` 方案（已定，已完成）

`/emergency/aiAlert`（AI预警）页面与 `/emergency/security` 同源（大华网关 `/calldevice/alarm/anfang/*`），"分类告警占比/明细"与 `security_status` 的 `ai_alert`/`ai_inspection` 语义高度重合。**决定：不单独建 `emergency_aialert` 意图，其独占能力并入 `security_status` 新增子类型**：

| security_status 子类型 | 来源接口 | 覆盖问法 | 状态 |
| --- | --- | --- | --- |
| `ai_alert`（已有） | `getAiAlertSituation` | 各类 AI 告警占比/分布/数量 | 已完成 |
| `ai_overview`（新增） | `getAlarmView`（`/deviceAlarm/aiAlarmView`） | 今日告警数、累计告警、算法类型数、识别准确率 | 已完成 |
| `ai_trend`（新增） | `getAlertSituation`（`/deviceAlarm/alertSituation`） | 近 7 天 / 近 30 天 AI 告警趋势 | 已完成 |
| `ai_alarm_list`（新增） | `getAlarmListWithType`（`/calldevice/alarm/anfang/alarmListWithType`） | 安防/管理/环境预警分类明细列表 | 已完成 |

落地约定：
- Python 侧改动：`classifier.py` 语料、`slots.py`、`security_status_handler.py`、`graph/security_status_langgraph.py` 的 `_JAVA_TOOL_MAP` 各加 2~3 个条目。
- Java 侧：在安防 MCP Server（现有 sidecar）中新增对应工具，不新建 server。
- 注意点：`ai_alarm_list` 含"管理预警/环境预警"，严格说不全属安防域，但对话场景下用户不区分页面边界，可接受；若将来平台建统一告警中心再拆分。
