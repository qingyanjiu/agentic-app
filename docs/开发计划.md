### 2.5 `device_query` 设备查询意图（已实现，对齐资产库口径）

与 `device_status`（统计口径：分类占比、在线率、维修趋势）区分，`device_query` 走**台账口径**：查具体某台/某类设备本身。

**2026-09-17 接口变更**：Java 侧新写了 `/mcp/devicequery` 端点（`PlatformDeviceQueryMcp`），设备清单/详情的权威口径从厂商透传改为**资产库**（平台自有的 `VISUAL_DEVICE_INFO` 纳管资产）。Python 侧据此改工具名、入参名、返回解析与追问话术，`mcp_server_config.yaml` 新增 `devicequery` server。

| 子类型 | 后端工具 | 覆盖问法 |
| --- | --- | --- |
| `device_list` | `device_query:listDevice` | 设备列表 / 有哪些设备 / A栋3楼的监控设备 |
| `device_detail` | `device_query:getDeviceDetail`（先用 `listDevice` 把名称/编号换成内部 `id`） | 某设备的详情 / 档案 / 参数 |

**设备类型码是 `syncSource`（八类，`DEVICE_TYPE_DICT` 按此收敛）**：

| `syncSource` | 含义 | 别名词（`extract_device_type` 用） |
| --- | --- | --- |
| `0` | 门禁设备 | 门禁 / 闸机 / 门禁控制器 / 门禁通道 |
| `1` | 道闸设备 | 道闸 / 车闸 / 车牌识别闸机 |
| `2` | 梯控设备 | 梯控 / 电梯控制 / 电梯 |
| `3` | 监控设备 | 监控 / 摄像头 / 摄像机 / 枪机 / 球机 / 半球 / 视频监控 |
| `4` | 入侵报警设备 | 入侵报警 / 周界报警 / 报警设备 / 红外报警 / 报警 |
| `5` | 广播设备 | 广播 / 音箱 / 喇叭 / 广播终端 |
| `6` | 水表 | 水表 / 智能水表 |
| `7` | 电表 | 电表 / 智能电表 |

> 别名词有重叠时（"车牌识别闸机" vs "闸机"、"入侵报警" vs "报警"）取**最长命中**，否则前者会被后者抢走判错类型（`slots.py::extract_device_type`）。
> 消防（灭火器/烟感）走 `emergency_fire`，网络设备/空调资产库里没有对应类型，均**不进** `device_query` 语料。

**后端返回结构**（解析见 `graph/device_query_langgraph.py::_iter_rows`）：

```json
{"code":200,"data":{"page":{"total":2,"size":100,"pages":1,"current":1},
 "data":[{"id":"1001","name":"A栋枪机","code":"CY-HIK-JK-001-0001","syncSource":"3",
          "deviceTypeName":"监控设备","status":"1","spaceId":"2001",
          "spaceName":"园区/A栋/3楼","personInChargeName":"张三","orgName":"安防部","maintained":"1"}]}}
```

- `status` 是**启用状态**（0停用 1启用 2维修 3报废），**不是在线/离线**——Java 侧特意在工具描述里标了这个坑，LLM 提示词（`_llm_format_device_query_result` 的 `code_rule`）也照此写明，避免把"启用"答成"在线"。
- `spaceName` 是位置全路径名（`园区/A栋/3楼`），回答位置类问题用它。
- `id` 是查详情的唯一凭据；`code` 是设备编号（如 `CY-HIK-JK-001-0001`），**两者不是一回事**。

落地约定：
- 槽位（`slots.py::extract_device_query_slots`）：`query_type`、`device_type`（`syncSource`，**可选**筛选）、`area`（区域+楼栋+楼层合并，如 `A栋3楼`）、`device_keyword`（设备名称或编号）。
- **列表无必填参数**：`listDevice` 的筛选参数（`syncSource`/`deviceType`/`status`/`name`/`code`/`spaceId`/`maintained`/分页）全是可选，不传就是全部设备，所以列表口径不再反问设备类型。
- **位置筛选**：后端只认 `spaceId`，Python 侧拿到的是位置名，故不下发；改为拉一页（`pageSize=200`）回来按 `spaceName` 在提示词里让 LLM 本地过滤（`_AREA_PAGE_SIZE`）。
- **名称/编号筛选**：下推给 `listDevice`（平台侧 `name` 模糊匹配、`code` 精确匹配）。先按 `name` 搜，搜不到再按 `code` 搜一次（`_search`）。
- **详情两步走**：详情接口只认内部 `id` → 先 `listDevice` 搜出设备 → 取 `id` 调 `getDeviceDetail`。完全相等（编号或名称）的唯一一条直接用；只有一条也用；多条且都不相等时**不猜**，把候选（名称/编号/位置）列给用户指定（`_pick_device` / `_format_candidates`）。
- 追问（`_get_missing_params`）：只有 `device_detail` 缺 `device_keyword` 时反问"请问您想查看哪台设备的详情？可以说设备名称或设备编号。"（handler 的 `generate_question` 与 graph 的 `ask_param` 文案必须逐字一致，由 `TestQuestionConsistency` 守着）。
- 设备编号正则 `DEVICE_CODE_RE`：资产库编号是多段带分隔符的（`CY-HIK-JK-001-0001`），旧的"字母+数字"写法会把它截成 `JK-001`，故改为"带分隔符的多段编号 + 短编码"两种形态都整串抽取。
- 子类型兜底：正则主判，落到 `device_list` 时用 embedding 分类器补判 `device_detail`（阈值 0.6）；但用户已明说"清单/列表/有哪些/所有/台账"等**列表措辞**时不再改判——实测"查下广播设备清单"会被判成 `device_detail` 0.75、"看下设备清单"0.83（连列表语料自身的例句都判不动），补语料收效甚微，故改为在 handler 层以正则为纲（`LIST_WORDING`）。残余边界：不带列表措辞的"查下A栋的监控设备"仍判 `device_detail`，会多问一句"哪台设备"，用户补充名称后照常返回。
- 已知边界：**只报编码、不带"设备/台"等名词的短问法**（如"CY-HIK-JK-001-0001的详情"，实测 0.53）过不了顶层阈值 0.65，会落到 `other`；带上名词即可命中（"CY-HIK-JK-001-0001这台设备的详情" 0.72）。曾尝试在语料中补编码样例，虽能把前者抬到 0.61（仍不达标），却把"园区有哪些设备"从 0.776 压到 0.748 而输给 `compositive_overview`，故**放弃该改法**。后续若要支持，建议在 Java 侧或 `app.py` 前置加编码正则分支，而不是继续调语料。
- 与厂商口径的关系：同一个端点上还有 `device_query:getVendorDeviceList` / `getVendorDeviceDetail`（`/calldevice/*` 透传，实时在线状态、按资产编号查），**本意图不用**；`device_status` 的统计子类型仍走 `/mcp/device`。该端点另有 5 个接口与 `/mcp/device` 重叠（`getEquipClass` 等，Java 侧刻意保留的重复），两边行为一致，任选其一即可，别改出差异。

### 2.6 `device_status` 兜底反问"哪类设备"（已实现）

**背景**：`device_status` 的 `query_type` 由正则抽取，正则没命中任何子类型时保留哨兵值 `count`。改造前 `count` 会一路走到 `call_tool`，查不到 `_JAVA_TOOL_MAP` 里的工具，于是回一句"该查询类型当前 MCP 后端暂不支持"——用户说"查下设备"（实测"设备情况"分类器也判 `count` 0.937）就会撞上这句。消防/周界早在案例 2 就改成了"兜底值 → 反问"，设备态势这次对齐。

**为什么反问的是"哪类设备"而不是 8 个统计口径**：设备域只有"设备列表/设备详情"两个**台账工具**（查设备位置、基本信息），统计口径的子类型（在线率、健康度、维修趋势…）只在用户明说时才走。笼统的"查下设备"落到设备列表最符合实际用法，也让两个域的工具口径一致。

**行为**（`agent/intent/handlers/device_status_handler.py` + `graph/device_status_langgraph.py`）：

| 轮次 | 输入 | 结果 |
| --- | --- | --- |
| 第一轮 | "查下设备情况"（正则 `count`，分类器也判 `count`） | 反问"请问您想查询哪类设备？门禁、道闸、梯控、监控、入侵报警、广播、水表，还是电表？"（选项即资产库八类 `syncSource`，与 §2.5 同一套口径） |
| 第二轮 | "监控" | `device_type=3`，`query_type` 落 `device_list`，调 `device_query:listDevice(syncSource=3)` 列设备（资产库口径） |
| 放弃 | 连续 3 轮答非所问 | 追问超限，回"追问次数过多，我先不继续了。" |

落地约定：
- **缺参判定**：`query_type ∈ {空, count}` 且 `device_type` 为空 → 缺 `device_type`（handler 与 graph 对称）；`device_type` 有值时 `init_state` 把 `query_type` 归一成 `device_list`，不会再问一遍。
- **类型回复不走常规合并路径**：设备态势正则里 `门禁` 会命中 `mj_online`（门禁在线率），但用户在回答"哪类设备"时只是在选类型，因此追问轮先用 `extract_device_type` 解析；回复里带"在线/离线/率/趋势/占比/统计"等统计口径词（如"门禁设备在线率"）时说明用户重说了完整问法，仍走常规路径按统计子类型处理。
- **不支持的指代**：与 `device_query` 一致，不解析"第一个"这类序数指代（选项词都是设备类型词，正则直接命中）；要加的话可参照消防的 `_pending_type_clarify` + `parse_ordinal_choice`。
- **残余边界**：`device_status` 没接"设备详情"，用户在反问后报具体设备名（如"MH-001"）不会被识别成类型，会再问一次，最终 `give_up`；查单台设备请走 `device_query`。
