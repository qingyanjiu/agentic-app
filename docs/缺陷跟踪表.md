## 1. 编制说明

### 1.1 目的

统一登记项目从 2026 年 5 月至今发现的缺陷、能力缺口与线上/联调问题，形成可追溯、可统计、可复核的缺陷台账，作为后续版本验收、回归测试和风险管理的依据。

### 1.2 统计口径

1. **一条缺陷 = 一个可独立定位和修复的根因**。同一根因引发的多个现象合并为一条，在明细中列出现象分支。
2. **重复条目只计一次**：`问题排查记录.md` 中「案例 16」有两个同编号小节，内容为同一问题（能源日期校验误伤「今天」），本表合并为 `BUG-202609-040`。
3. **能力缺失也纳入跟踪**：项目早期部分缺陷表现为「功能没有建设」，类型记为「能力缺失」，与功能缺陷分开统计，避免与真正的代码错误混淆。
4. **状态判定偏保守**：
   - `已关闭`：有明确验证记录（评测数据、线上复现消失、单测落地且结果有记录）；
   - `已修复`：代码已改、文档有修复说明，但容器内验证步骤未留下执行记录；
   - `部分关闭`：主问题已处理，仍有子项移交后续批次或接受失败；
   - `挂起` / `接受风险`：明确不修或暂不修，见第 6 节。
5. 按用户既有约定，本表编制过程中**不代跑 pytest / 评测脚本**；验证状态以仓库文档中的记录为准，测试命令随条目给出。

## 2. 字段与等级定义

### 2.1 字段说明

| 字段 | 说明 |
| --- | --- |
| 缺陷ID | `BUG-YYYYMM-NNN`，按发现月份编号；跨月修复不改变原编号 |
| 发现日期 | 首次记录/复现日期，非修复日期 |
| 模块 | 缺陷所属功能模块或工程域 |
| 缺陷标题 | 一句话描述「什么场景下出了什么问题」 |
| 类型 | 功能缺陷、逻辑缺陷、集成缺陷、配置缺陷、数据/语料缺陷、前端缺陷、架构缺陷、能力缺失、工程缺陷、安全缺陷 |
| 严重程度 | S1~S4，见 2.2 |
| 优先级 | P0~P3，见 2.3 |
| 状态 | 已关闭、已修复、部分关闭、挂起、接受风险，见 2.4 |
| 修复/关联提交 | 能定位到的 Git 短哈希；无单独提交的填「工作区修复」并注明文档依据 |
| 来源 | 排查记录案例号、评测记录编号、评审条目或提交说明 |

### 2.2 严重程度

| 等级 | 名称 | 判定标准 |
| --- | --- | --- |
| S1 | 致命 | 服务无法启动/不可用；核心查询全线失败；数据静默错误；前端回合锁死；契约完全对不上 |
| S2 | 严重 | 主要功能不可用或结果错误，但有绕行；关键多轮场景失效；重要接口报错 |
| S3 | 一般 | 局部功能/边界场景错误；体验或文案问题；有明确 workaround |
| S4 | 轻微 | 工程规范、格式、注释、轻微体验问题，不影响功能 |

### 2.3 优先级

| 等级 | 含义 | 处理时限（建议） |
| --- | --- | --- |
| P0 | 立即处理，阻塞发布/联调 | 当日 |
| P1 | 本迭代内处理 | 3 个工作日内 |
| P2 | 排期处理 | 当前版本内 |
| P3 | 择期处理 | 可延后 |

### 2.4 状态与流转

```
新建 → 已确认 → 处理中 → 已修复 → 已验证 → 已关闭
                                  ↘ 部分关闭（子项移交）
        ↘ 挂起（等待依赖/排期）
        ↘ 接受风险（评估后不修）
```

本表 5 月起的历史条目已统一回填到上述状态，不保留「新建/处理中」中间态。

### 2.5 编号规则

- `BUG-202605-001`：2026 年 5 月第 1 条；
- 月份内按发现日期递增；
- 同一根因的后续回归不新开编号，在原条目「验证/备注」中追加；
- 能力缺失条目同样占用编号，类型标为「能力缺失」。

### 3.4 关键结论

1. **9 月是缺陷高发期**：48 条，占 69.6%。原因是多域 MCP 集中接入 + 多轮对话状态机集中联调，问题从「单轮分类准不准」扩展到「多轮接不接得住」。
2. **最高频根因是「契约/口径不一致」**：MCP 端点、工具名、返回字段、设备类型码、时间口径、楼层写法，均在联调时集中暴露。对应措施是「先 discovery 再写映射」，见 `BUG-202609-004`。
3. **第二高频根因是「状态机只覆盖理想路径」**：追问态、完成态、确认态、取消态、省略式追问之间的边界，是 9 月缺陷的主要来源。
4. **10 月无提交，不等于无风险**：9 月末的 5 条部分关闭项、1 条挂起项、2 条接受风险项仍在跟踪，见第 6 节。
5. **11 月问题集中在「业务 vs 场景」分流**：场景通道只有动作工具，数据问法一旦误入就会答非所问，已通过「数据词否决 + 问句规则 + 向量兜底 + 强场景词」四层收敛。

## 5. 重点缺陷明细（S1/P0 及关键 S2）

### 5.1 BUG-202608-001：语音识别与 MCP Skill 导入失败导致应用无法启动

- **发现阶段**：容器启动自测
- **现象**：`app.py` 导入 `McpSkillAgent`、`VoiceRecognizer`、`TextCorrector` 时即报错，整个服务起不来。
- **根因**：相关模块依赖的运行时/模型在目标容器中不完整，导入期异常未被隔离。
- **修复**：`d3f0824` 注释掉 `McpSkillAgent`、`skills.mcp_agent`、`asr.voice_asr`、`asr.text_corrector` 的导入与 `/mcp_skill` 路由，先恢复主服务启动。
- **验证**：主服务可启动；ASR/MCP Skill 功能暂时下线。
- **备注**：属降级规避，根因未根治，见 `RISK-01`。

### 5.2 BUG-202608-002：MySQL 不可达导致会话建立失败

- **发现阶段**：联调/本地启动
- **现象**：进入对话即报错，无法建立会话。
- **根因**：`memory_persistor.type = mysql`，连接串指向不可达的 `192.168.100.58`，建连失败阻断会话初始化。
- **修复**：`d386b68` 将连接串改为 `10.204.146.144`；`4cf5d44` 将持久化切到 `json`，便于本地调试。
- **验证**：本地/容器不依赖 MySQL 可正常对话。
- **备注**：生产仍建议使用 MySQL，需在部署环境确认连接串与网络可达性。

### 5.3 BUG-202609-001：单个 MCP 端点 404 拖垮全部域

- **发现阶段**：多域联调
- **现象**：人员、安防、食堂、车辆、信息、能源、会议全部报「xxx 工具未加载」，不止消防。
- **根因**：`MultiServerMCPClient(全部 8 个 server).get_tools()` 用 TaskGroup 并发连接，任一 server 失败即整组异常；当时消防端点 `/mcp/fireStatus` 返回 404，导致每个域的 `load_xxx_tools()` 都拿到空工具。
- **修复**：`4131df3` 将 `mcp_client/mcp_loader.py` 改为逐 server 独立加载，`asyncio.gather(..., return_exceptions=True)`，单点失败只告警并跳过，其余域照常返回。
- **验证**：启动日志可按 server 看到「加载到 N 个工具」；单个后端离线不再影响其他域。
- **教训**：多 server 聚合加载必须做单点隔离。

### 5.4 BUG-202609-004：消防端点、工具名、返回字段三处契约不一致

- **发现阶段**：消防域联调
- **现象**：实时告警必失败；台账/告警列表字段对不上。
- **根因**：Python 侧按命名规律和接口文档「猜」契约：
  1. 配置 `/mcp/fireStatus`，实际暴露 `/mcp/fire`；
  2. 映射 `fire:getAlarmList`，实际注册 `fire:getFireAlarmList`；
  3. 台账/告警字段按旧文档平铺设计，实际监测项在 `dataMap`，告警时间是毫秒时间戳。
- **修复**：`4131df3` 改端点、改工具名、按真实 payload 重写压缩函数（展平 `dataMap`、格式化 `*Time`）。
- **验证**：`/mcp/fire` 返回 200，`tools/list` 与 `_JAVA_TOOL_MAP` 逐名一致，真实调用可出数。
- **教训**：接口文档 ≠ 真实契约，接入前必须做 discovery。

### 5.5 BUG-202609-009：追问轮 slots 被子类型默认值覆盖

- **发现阶段**：多轮对话走查
- **现象**：问「李四昨天的轨迹」→ 缺人名追问 → 答「张三」→ 最后查的是人数统计；问「告警详情」→ 答「第3条」→ 调了无参列表工具，ID 被丢弃。
- **根因**：追问轮 `handle_reply` 用本轮回复单独重新抽槽再合并，子类型字段没有默认值守卫；person 的守卫还写错成 `v != "location"`。
- **修复**：`7becaff`、`ff75669` 给各 handler 的 `extract_slots` 增加 `is_followup` 参数，追问轮只抽填空字段、不重判子类型；子类型仅在未确定时补填。
- **验证**：追问补充人名/ID 后子类型保持不变；`tests/test_handlers.py`、`test_context_scenarios.py` 覆盖。
- **教训**：追问轮与首轮抽槽语义不同，不能复用同一套「默认值」。

### 5.6 BUG-202609-010：省略式追问实体查错人

- **发现阶段**：多轮对话走查
- **现象**：「张三现在在哪」→ 完成后「那李四呢」→ 仍返回张三；连续追问后 `original_query` 越来越长。
- **根因**：省略式追问把「上轮原话 + 本轮输入」拼成一个串整体抽槽，`extract_person_name` 按固定名单顺序取第一个命中，永远先命中张三；拼接串又回写 `original_query`，造成滚雪球。
- **修复**：`3f6f545`、`ff75669` 改为「拼接串只喂分类器，槽位只用本轮输入；本轮没抽到的实体从上一轮继承；`original_query` 保持首轮原话」。
- **验证**：`tests/test_context_scenarios.py` 的 C6 场景覆盖「那李四呢」；连续追问不膨胀。
- **教训**：拼接串的用途要解耦——分类用完整语义，抽槽用本轮输入。

### 5.7 BUG-202609-017：懒加载空图缓存投毒

- **发现阶段**：服务恢复验证
- **现象**：Java 侧 overview 服务已恢复、工具名也一致，但综合态势仍报 `overview:getBasicInfo 工具未加载`。
- **根因**：各域懒加载 `if _xxx_graph is None: build_xxx_graph(tools)`，首次查询撞上后端不可用 → `tools={}` → 空图正常编译并永久缓存，之后不再重试。
- **修复**：`get_xxx_graph()` 在工具为空时不缓存并返回 `None`，`run_xxx_graph()` 发「MCP 工具暂时不可用」error 事件，下次查询自动重试；会话状态按完成态保留。
- **验证**：停掉某域服务再问 → 明确报错；服务恢复后不重启 Python 再问 → 正常出数。
- **教训**：「首次初始化并永久缓存」必须回答失败重试策略；空图也是图，入缓存前要做依赖空校验。

### 5.8 BUG-202609-019：设备查询 `deviceType` 契约不符

- **发现阶段**：Java MCP 联调
- **现象**：设备查询传参与后端实际契约不一致，类型筛选不生效或报错。
- **根因**：Python 侧按旧文档将 `deviceType` 当作八类、可选参数；Java 侧实际收敛为五类且必填。
- **修复**：`723b590` 对齐后端真实契约，收敛为五类并改为必填；同步 slots、handler、graph、测试与文档。
- **验证**：`tests/test_graphs.py`、`test_handlers.py`、`test_slots.py` 覆盖五类映射与必填校验。
- **后续**：`57c6327`、`e68b314` 进一步将清单/详情切换到资产库 `/mcp/devicequery` 口径。

### 5.9 BUG-202609-036：取消后前端永久转圈

- **发现阶段**：时间澄清追问冒烟
- **现象**：追问中回「不用了」，出现「已取消查询」后加载指示永久转圈，输入框锁死。
- **根因**：`handle_reply` 返回 `give_up` 后，`app.py` 只发 `{"type":"answer"}` 就 `continue`，没发 `{"type":"done"}`；前端 `turnActive` 只由 `done`/`ask`/`error` 复位，`answer` 不结束回合。
- **修复**：`3f6f545` 在 give_up 分支 answer 之后补发 done，对齐 graph 约定。
- **验证**：取消后转圈立即消失、输入框恢复；再发新查询正常。
- **教训**：`answer` 必配 `done`，所有绕过 graph 的手写发送分支都要逐个核对。

### 5.10 BUG-202609-043：确认态「查」字子串误判同意

- **发现阶段**：2026-09-23 冒烟 T4
- **现象**：确认等待期用户改发新查询「查一下人员位置」，被 `AGREE_KEYWORDS` 的单字「查」子串命中，误当成同意，旧查询被继续执行。
- **根因**：同意判定用子串匹配，而不是整句语义匹配。
- **修复**：`ff75669` 新增 `is_confirm_agree()`，去标点/空白/结尾语气词后必须整句等于确认白名单；带业务词的长句一律落到 `re_ask`，交给跨域接管窗口。
- **验证**：确认态发新查询不再被执行；「好的」「可以」「是的」仍能确认。
- **教训**：短词白名单不能用子串匹配，尤其是单字动词。

### 5.11 BUG-202611-001：场景通道误吞数据查询

- **发现阶段**：UE 场景控制线上使用
- **现象**：「我现在查询一楼监控数据」→ 场景图下发 `scene_show_device_category`，回答「已下发动作」，但用户要的是数据查询。
- **根因**：业务最高分 `security_status=0.6474`，差 0.0026 未过 0.65 → `other`；场景分 0.6309 刚过 0.60 → 命中「业务 other 且场景命中就走场景」；场景图只有动作工具，LLM 只能把「查询监控数据」规划成最接近的「显示监控点位」。
- **修复**：`b87e3b1` 新增 `_DATA_QUERY_CUES` / `is_business_query`，`should_route_scene` 前置否决——带数据词且无明确场景动作的问法不落场景；同时补 6 条「楼层+监控+数据」设备查询语料。
- **验证**：「查询一楼监控数据」→ `device_query 0.6895` 走业务；「切到3楼」「重置视角」仍走场景；全量评测 218/240 零回归。
- **教训**：业务判 other ≠ 可以交给场景；场景通道只有动作工具，数据问法必须独立否决。

### 5.12 BUG-202611-002：设备查询工具未加载

- **发现阶段**：UE 场景联调同日
- **现象**：分流正确，但执行时报 `device_query:listDeviceOnly 工具未加载`。
- **根因**：
  1. `get_mcp_tools()` 一次加载配置里 13 个 server，超时包在整组外；
  2. 业务端点 `10.204.146.228:2222` 不可达，TCP 连接挂起，15s 到点整组取消；
  3. 设备查询拿到空字典，且空图被缓存，sidecar 恢复后也不重试。
- **修复**：`b87e3b1` 将业务端点改为 `10.204.146.44:2222`；新增 `get_mcp_tools_for_server()` 单 server 定向加载、单独超时；设备查询只加载 `devicequery`；工具为空不缓存；前端错误不再拼 traceback。

### 9.1 BUG-202611-008：场景 env_time 仍按口语枚举下发，未换算成 HH:MM:SS

| 字段 | 内容 |
| --- | --- |
| 缺陷编号 | BUG-202611-008 |
| 发现日期 | 2026-11-06 |
| 发现阶段 | 前端联调 / 线上日志走查 |
| 所属模块 | 场景控制（`graph/scene_control_langgraph.py`、`agent/intent/classifier.py`） |
| 关联工具 | `scene_set_env`（`env_time` 参数） |
| 缺陷类型 | 集成缺陷（前后端契约不一致） |
| 严重程度 | S2 |
| 优先级 | P1 |
| 状态 | 已修复（待验证） |
| 关联提交 | 本次修复提交 |

**现象**

前端日志显示服务端下发的动作帧为：

```text
[SceneClient] 收到服务端指令 event=action ... params={"env_time":"中午"}
[SceneClient] 收到服务端指令 event=action ... params={"env_time":"白天"}
```

sidecar 实际契约要求 `env_time` 是 24 小时制时间字符串（如 `"12:00:00"`），
上述口语值不是合法入参，UE 侧无法按时刻执行。同时用户说「下午一点」时，
系统也没有换算成 `13:00:00`。

**根因**

1. 旧实现按枚举口径设计 `env_time`（`白天/傍晚/夜晚`），只做枚举收敛，
   没有「口语时刻 → `HH:MM:SS`」的解析；
2. 参数归一化只在 sidecar schema 声明了 `env_time.enum` 时触发，
   schema 改成 `type: string` 后归一化被整体跳过，LLM 返回的口语值原样透传；
3. 规则兜底只识别时段词，不识别「早上9点 / 下午一点半 / 19:15」这类具体时刻；
4. 场景强特征正则未覆盖「时间切到/改成/调到…」句式，「时间切到早上9点」
   在向量分不足时会被分流到业务通道。

**修复**

1. `scene_control_langgraph.py` 新增中文时刻解析链路：
   - `_parse_scene_time()`：支持 `HH:MM(:SS)`、`N点/M分`、`半/一刻/三刻`、
     中文数字（含「十/十二/二十三/零五」）、全角数字与冒号；
   - `_apply_period()`：按 `凌晨/早上/上午/中午/下午/傍晚/晚上/夜晚/深夜` 等
     时段换算 24 小时制（下午一点 → 13 点，晚上十二点 → 00 点）；
   - `_format_clock()`：统一输出 `HH:MM:SS`；
   - `_normalize_env_args()` 改为**用户原话优先于 LLM 返回值**：
     原话能解析出时刻就以原话为准，LLM 值仅作兜底；两者都解析不出时丢弃
     `env_time` 并追问，不再把口语值下发。
2. LLM 规划提示词明确要求 `env_time` 填 `HH:MM:SS`，并给出「下午一点 → 13:00:00」
   的示例，禁止填「中午/白天/傍晚」这类口语词。
3. 规则兜底的环境分支改用 `_parse_scene_time()`；只识别到「环境/天气」但
   没有具体效果时改为追问，不再下发空参数或猜测值。
