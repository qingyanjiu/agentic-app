## 案例 1：所有旧 MCP 报「xxx 工具未加载」

**日期**：2026-09-10
**影响**：人员/安防/食堂/车辆/信息/能源/会议全部域查询失败；新增的消防域连带拖垮

### 现象

前端收到：

```json
{"event": "custom", "data": {"type": "error", "content": "canteen:getWeekMenu 工具未加载"}}
{"event": "custom", "data": {"type": "error", "content": "person_status:getTodayPersonnelAffairs 工具未加载"}}
```

所有旧域全部报错，不止一个模块。

### 根因（两个因素叠加）

1. **Java sidecar 上消防端点未部署**：`POST http://host.docker.internal:2222/mcp/fireStatus` 返回 **404**（当时配置里刚加了 `fire` 条目）。
2. **mcp_loader 把全部 server 塞进一个客户端**：`MultiServerMCPClient(全部8个server).get_tools()` 内部用 TaskGroup 并发连接，**任何一个失败 → 整组异常**。于是每个域的 `load_xxx_tools()` 全部拿到空 tools → 全部「工具未加载」。

app.log 中的对应痕迹：

```
ERROR - graph.canteen_status_langgraph - 加载 MCP 食堂工具失败: unhandled errors in a TaskGroup (1 sub-exception)
DEBUG - mcp.client.streamable_http - Connecting to ... /mcp/fireStatus
INFO  - httpx - HTTP Request: POST .../mcp/fireStatus "HTTP/1.1 404 "
```

### 排查思路

- 「工具未加载」是 graph `call_tool` 节点里 `tools.get(java_tool_name)` 为空的分支 → 说明工具**加载阶段**就失败了，不是调用失败
- grep app.log 中 `工具失败|工具超时|404` 定位到加载报错与 404 的端点
- 关键认知：`get_mcp_tools()` 一次连**配置里所有** server，单点故障会传染

### 修复

`mcp_client/mcp_loader.py` 改为**逐 server 独立加载**：

- `asyncio.gather(..., return_exceptions=True)` 并发连各 server
- 单个失败只打 `WARNING: MCP server [fire] 工具加载失败，跳过该服务`，其余照常返回
- 每个 server 成功打 `INFO: MCP server [xxx] 加载到 N 个工具`，启动日志可直接看出哪个后端没就绪

### 教训

- **一个后端没就绪不应拖垮全部域**：多 server 聚合加载必须做单点隔离
- 新增 `mcp_server_config.yaml` 条目前，先用 curl 确认端点存在：
  `curl -X POST http://localhost:2222/mcp/fireStatus`
- Java 侧新增模块时，Python 侧配置**同步上线**要约定好先后顺序
- 另见「案例 4」：端点路径/工具名/返回字段三处与 Java 侧契约对不上的排查与协同开发约定

## 案例 2：消防查询返回「该查询类型当前 MCP 后端暂不支持」

**日期**：2026-09-10
**影响**：消防态势笼统问法必然失败

### 现象

用户问「查下最新的消防」，返回：

```json
{"event": "custom", "data": {"type": "answer", "content": "该查询类型当前 MCP 后端暂不支持，请稍后再试。"}}
```

### 根因

这不是异常，是 `call_tool` 节点的**守卫分支**：槽位 `query_type` 在该域 `_JAVA_TOOL_MAP` 里找不到映射时主动返回的兜底话术。

链路：

1. 「查下最新的消防」太笼统：正则抽不到子类型落到 `count` 兜底，embedding 分类器（`classify_fire_sub_type`）也只判出 `count`
2. 消防的 `_JAVA_TOOL_MAP` 只有 4 个合法值（`fire_assets` / `fire_alarm_num` / `fire_alarm_list` / `month_repair`），**没有 `count`**
3. `call_tool` 里 `state["slots"].get("query_type") or "count"` 的默认值是从人员/能源 graph 抄来的——那些域 `count` 是合法 key，消防不是 → 笼统问法**必然**进守卫分支

app.log 证据：

```
[classify_intent] query=查下最新的消防, intent=emergency_fire, score=0.7864
[classifier]      query=查下最新的消防, fire_sub_type=count, score=0.8426
WARNING - query_type=count 暂不被 Java MCP 后端支持
```

### 修复

不给默认值，改为**反问用户**（沿用 graph 现成的 `check_missing_params → ask_param` 追问机制）：

- `graph/emergency_fire_langgraph.py`：`check_missing_params` 把 `query_type` 为空/`count` 计入缺失参数；`ask_param` 反问「请问您想查询哪类消防数据？设备台账、告警统计、实时告警，还是月度报修？」
- `agent/intent/handlers/emergency_fire_handler.py`：`_get_missing_params` / `generate_question` 同步该逻辑，保持会话状态一致
- 反问轮不重新分类意图（`app.py` 有活跃状态时跳过 classify），用户回「实时告警」等选项词由正则直接命中
- `call_tool` 的守卫分支保留作安全网，正常流程到不了

### 教训

- **多个 graph 之间复制 `_JAVA_TOOL_MAP` 默认值时**，先确认该默认值在目标域的映射里存在
- 意图识别成功 ≠ 子类型识别成功；枚举型槽位抽不到时，反问比兜底报错体验好
- 反问的选项措辞要**与 slots.py 正则关键词对齐**，用户照着念就能被识别

## 案例 3（附带发现）：「实时告警」顶层意图被分到安防而非消防

**日期**：2026-09-10
**状态**：已定界关闭（2026-09-17，随语料扩写计划落地）

### 现象

无会话状态时首次提问「实时告警」，顶层意图分类为 `security_status`（score 0.6920），而非消防的 `fire_alarm_list`。

### 说明

安防与消防的示例向量存在竞争（`EMERGENCY_FIRE_STATUS_EXAMPLES` / 安防对应示例集）。后续如复现，可给消防示例集补充「实时告警」类样例后重新预计算中心向量。

- 用户拍板：裸「实时告警」→ 消防 `fire_alarm_list`；泛「告警列表/今天园区有哪些告警」→ 安防 `alarm_list`
- 核实：`fire_alarm_list` 组其实**已收录**「实时告警」，输在消防域整体语料太薄（~56 条）导致顶层中心拉不过安防——修复路径不是补词条，而是**批 1 消防全域扩写**后复测
- 评测基线（docs/语料评测记录.md 记录 #1）：该用例实际走到 `security_status/alarm_detail`（0.7138），列入 incident 跟踪，批 1 后必须转绿

## 案例 4：消防域联调「对不上」——端点路径、工具名、返回字段三处不一致

**日期**：2026-09-10
**影响**：消防态势查询失败或返回内容残缺（实时告警必失败、台账/告警列表字段全对不上）

### 现象

消防模块开发时按命名规律和接口文档「猜」了三处契约，联调时全部对不上：

1. **端点 404**：`mcp_server_config.yaml` 配的是 `/mcp/fireStatus`，Java sidecar 实际暴露的是 `/mcp/fire`
2. **工具名不匹配**：`_JAVA_TOOL_MAP` 里写的是 `fire:getAlarmList`，实际注册的是 `fire:getFireAlarmList` → 即使端点通，实时告警也必然「工具未加载」
3. **返回字段对不上**：台账压缩的 keep 字段按旧接口文档猜的（`deviceName/pressure/...`），实际返回是 `assetsName/offLineFlag/.../dataMap`（压力/液位/电量/倾角在 `dataMap` 数组里）；告警列表同理，且 `nowAlarmTime` 是毫秒时间戳

### 根因

**Python 侧单方面按「约定俗成」推断 Java 侧契约，没有在接入前做发现（discovery）验证**：

- 端点路径照搬其他模块规律（`/mcp/xxxStatus`），消防偏偏是 `/mcp/fire`
- 工具名按文档里的平台接口名直译（`getAlarmList`），Java 侧统一加了 `Fire` 前缀
- 返回结构照接口文档（sjy/V1.0）平铺字段设计，实际平台返回把监测项收进了 `dataMap`

### 排查

逐个契约点用真实端点验证，而不是看文档猜：

```bash
# 1. 探测端点是否存在（initialize 请求，看 HTTP 状态码）
for p in fireStatus fire; do
  curl -s -o /dev/null -w "%{http_code}\n" -X POST \
    "http://host.docker.internal:2222/mcp/$p" \
    -H "Content-Type: application/json" \
    -H "Accept: application/json, text/event-stream" \
    -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{...}}'
done
# 结果：/mcp/fireStatus -> 404，/mcp/fire -> 200

# 2. 列出端点上真实注册的工具名，与 _JAVA_TOOL_MAP 比对
docker exec langchain-agent-dev python -c "
from langchain_mcp_adapters.client import MultiServerMCPClient
client = MultiServerMCPClient({'fire': {
    'transport': 'streamable_http',
    'url': 'http://host.docker.internal:2222/mcp/fire'}})
for t in asyncio.run(client.get_tools()): print(t.name)
"
# 结果：fire:getFireAlarmList / fire:getFireAlarmNum / fire:getFireAssets / fire:getMonthRepair

# 3. 返回字段：直接调一次工具看真实 payload，再改压缩函数
```

### 修复

- `mcp_client/mcp_server_config.yaml`：`fire.url` 改为 `http://host.docker.internal:2222/mcp/fire`
- `graph/emergency_fire_langgraph.py`：`_JAVA_TOOL_MAP["fire_alarm_list"]` 改为 `fire:getFireAlarmList`；`_ASSET_KEEP_FIELDS` 改为实际字段；`_compact_fire_assets` 单独展平 `dataMap`（`monitorName=monitorValueunit`）；告警列表 keep 字段改为 `title/alarmTypeName/assetsName/areaName/alarmLevel/handleStatus/nowAlarmTime/alarmReason`，并在 `_compact_fire_rows` 中对 `*Time` 纯数字字段做毫秒时间戳格式化（`MM-dd HH:mm`）

### 教训

- **接口文档 ≠ 真实契约**。文档（尤其标了版本号的第三方接口）可能滞后或简化，接入前必须对真实端点做 discovery
- **不要按命名规律推断路径/工具名**。端点路径、工具名是 Java 配置类里的字面量，只有 `tools/list` 的结果算数
- **压缩/解析逻辑必须对着真实 payload 写**，先调通一次真实调用再写字段映射

### 附：与 Java 端协同开发的约定建议

1. **契约先行**：Java 侧每新增一个 MCP server，先在接口文档中登记三项——端点路径（如 `/mcp/fire`）、工具名清单（如 `fire:getFireAssets`）、每个工具的入参/出参 JSON Schema（最好是真实响应样例）。Python 侧照抄登记内容配置，不自行推断
2. **discovery 脚本常备**：把上面「curl 探测 + tools/list」两个脚本固化到仓库（如 `scripts/probe_mcp.py <url>`），作为每次新增/变更 server 后的第一步联调动作；`tools/list` 输出与 `_JAVA_TOOL_MAP` 逐名比对，差异即报错
3. **命名规范双方对齐**：约定端点 = `/mcp/{domain}`、工具名 = `{domain}:{动作}`，并由 Java 侧在 `XxxMcpServerConfig` 类名/注释中与路径对应；命名规范用于**生成和评审**，不用于**猜测**
4. **联调 checklist**：新增模块时按顺序确认——① 端点 200 ② tools/list 名称与映射一致 ③ 真实调用一次拿到 payload ④ 压缩/解析字段与 payload 对齐 ⑤ 端到端问句验证。任何一步不过先回查契约，不改代码硬凑
5. **变更同步**：Java 侧改端点/工具名/返回结构时，同步更新接口文档并知会 Python 侧；Python 侧的 probe 脚本可回归验证

## 案例 5：追问态说新需求，被复读问题吞掉

**日期**：2026-09-10
**状态**：已按方案 3 修复（app.py 追问分支 re_ask 处补跑 classify_intent，识别其他域且过阈值 → 清状态、按新意图走全新流程；本域/other 维持追问）

### 现象

消防反问「请问您想查询哪类消防数据？…」等待期间，用户直接说新需求「今天园区进出分别多少人」（人员态势），机器人不复读不变通，原样再问一遍：

```
您可能没理解我的问题。请问您想查询哪类消防数据？设备台账、告警统计、
实时告警，还是月度报修？或者您可以直接说新的需求。
```

用户重复该新需求的话，第 3 次触发 give_up 清空会话，**第 4 次**才能正常路由到人员态势。

### 根因（三层）

1. **架构层：追问态没有「新意图接管」通道**。`app.py` 中有活跃会话状态时**完全跳过意图分类**（当初的性能优化："避免追问轮重复编码"），固定进当前模块的 handler；`is_related()` 退化为纯关键词匹配，识别不了"这是别的域的新需求"。当前任务仅有的逃生口：说拒绝词（"算了/取消"），或连续 3 次不相关被踢出
2. **话术层：re_ask 文案承诺了代码没有的功能**。「或者您可以直接说新的需求」——流程里根本没有这条路。该文案是各 handler 共用模板，属于话术与实现脱节
3. **时机层：为什么现在才暴露**。之前消防识别不出类型直接答「暂不支持」即结束（无 ask 事件 → 会话清空），不停留在等待态；加了反问流程后消防**高频长时间停在追问态**，跨意图打断自然浮现。该缺口**所有域都有**（安防追问时问会议的事同样复读），只是其他域追问窗口短、且时间类追问能被 is_related 规则②的时间词接住，一直没被踩到

### 执行链路（日志佐证）

`classify_intent` 当天只跑 4 次，最后一条是 17:05「那说说消防吧」；「今天园区进出分别多少人」**从未进过分类器**，与代码路径推断一致：

```
app.py:911   有活跃状态 → 跳过 classify_intent（top_intent=None）
app.py:917   固定进消防追问分支 → EmergencyFireHandler.handle_reply()
is_related() 四条规则逐一不命中：
  ① 无拒绝词  ② 缺的是 query_type 不是 date  ③ len>4  ④ 无消防关键词
  → 判「不相关」→ unrelated_count=1 (<3) → re_ask 复读
```

### 附带发现：反向误判坑

`is_related` 规则④的关键词过宽：追问态下新需求若带「设备/告警/报修」等字样（如「会议室设备怎么预约」），会被**误判为相关** → 抽不出子类型 → 照样复读。比"不相关"更迷惑。

### 修复方向（待拍板）

| 方案 | 做法 | 代价 |
|---|---|---|
| **3（推荐）** | `is_related=False` 时先跑一次 `classify_intent`：识别出**其他域**意图且过阈值 → 放弃当前任务、按新意图走全新流程；仍是本域/other → 维持 re_ask | 仅疑似跑题时付费编码，兼顾成本与体验；顺带缓解反向误判 |
| 1 | 追问态每次回复都先分类 | 每轮多一次模型编码，正是当初优化掉的 |
| 2 | 只改文案：删「或直接说新的需求」，改「如需查询其他内容请先回复取消」 | 零风险但体验差，反向坑仍在 |

无论选哪个，re_ask 模板文案都要改——**不能承诺不存在的功能**。

### 教训

- **追问/多轮态是意图识别的盲区**：为省编码跳过分类器，就把"用户跑题"的识别压给了关键词启发式；凡有等待态的对话系统，必须设计新意图接管通道
- **话术是接口**：给用户的每句提示都对应一条代码里真实存在的路径，共享模板文案尤其要定期对照实现
- **在追问流程上加功能前，先检查会话状态生命周期**：让流程更多地"停在中途"的改动（如本例的反问），会放大原有状态机未覆盖的边界场景

## 案例 6：用户答「就第一个吧」，反问被复读

**日期**：2026-09-10
**状态**：已修复（方案 1+2：选项清单存会话状态 + 通用序数解析）

### 现象

消防反问「请问您想查询哪类消防数据？设备台账、告警统计、实时告警，还是月度报修？」，用户答「**就第一个吧**」（指设备台账），机器人判为"不相关"，原样复读问题。

### 根因：指代消解缺失

用户用「第一个」指代上一轮 bot 列出的选项——序数指代（anaphora），解析必须依赖上一轮的选项清单。而管道对每句回复**独立**处理：

1. **选项列表问完就扔**：`ask_param` 反问完，4 个选项没有存进 slots，后续无从解析指代。对比：日期澄清有现成范式（`vague_date` 存 `_pending_date_clarify` + `_date_options`，`handle_reply` 在 `is_related` **之前**拦截解析），子类型反问没做同样处理
2. **抽取层够不着**：`extract_slots` 只对当前句做正则/embedding，「就第一个吧」两个都命中不了
3. **短回复规则也救不了**：`is_related` 规则③ len≤4，而「就第一个吧」恰好 5 个字；但即使回「第一个」（3 字，命中规则）也没用——抽出仍为 `count`，merge 守卫不许覆盖 → graph 再问一遍。**缺口不在 is_related 阈值，而在"序数 → 选项"解析层根本不存在**

注：案例 5 加的新意图接管救不了它，也不该救——「就第一个吧」分类为 other，是没被听懂的当前意图回答，不是新意图。

### 修复（方案 1+2）

1. **通用序数解析** `agent/intent/slots.py: parse_ordinal_choice(query, max_index)`：支持「第一个 / 第1个 / 第 2 个 / 就第三个吧 / 1 / 2」，1-based 返回，越界/解析不到返回 None；不带「第」前缀的句子（如"近三天"）不误命中
2. **graph `ask_param`**：反问类型时把 `_pending_type_clarify` + `_type_options`（`_TYPE_OPTIONS` 固定顺序）存进 slots（仿日期澄清模式）
3. **handler `handle_reply`**：在日期拦截之前加类型澄清拦截，`_resolve_type_choice` 先序数后文本（文本路径复用 `extract_emergency_fire_slots`，选项词命中即返回）；命中 → 设 `query_type`、清标记、continue；**解析失败不死缠**，落回常规流程，保住案例 5 的新意图接管
4. **日期澄清接入序数**：`_pending_date_clarify` 分支里「第一个」→ 改写 q 为选项文案（如「近三天」），走既有句式解析
5. **标记清理**：类型明确后（无论走哪条路径）清掉 `_pending_type_clarify` / `_type_options`，防止陈旧标记影响后续轮次

### 教训

- **凡是 bot 列出选项的追问，必须预期用户用「第 N 个 / N / 就第一个吧」回答**；选项清单是对话状态的一部分，问完就丢等于让用户只能复读选项原文
- 短回复兜底规则（len≤4）只是让系统"态度好一点"，不解决"听懂"
- 追问拦截分支解析失败时应**落回常规流程**而不是就地死缠，否则会挡住其他追问轮机制（如新意图接管）

## 案例 7：LLM 回答里随口追问，用户确认后被兜底拒绝

**日期**：2026-09-11
**状态**：方案 A 已实施——9 个域的 `_llm_format_*_result` prompt（person/security/canteen/vehicle/information/energy/meeting/fire/device）统一加两条禁令：空数据只如实说明、不得建议查其他时间段，且禁止任何追问/提议/反问；方案 B（空结果显式 ask + 确认词解析）留作后续正解

### 现象

```
用户：今天园区安防事件有哪些？
bot：今天没查到园区安防事件的告警数据，可能是今天暂时没有告警，或者数据还没同步。
     要不要我帮你查一下其他时间段？
用户：可以
bot：对不起，我目前掌握的能力无法解决你的问题
```

### 根因：LLM 输出与状态机协议脱节

第一轮那句「要不要我帮你查一下其他时间段？」**不是系统发出的追问**：

1. 安防 graph `call_tool` 查到空数据，[security_status_langgraph.py](../graph/security_status_langgraph.py) 的 LLM prompt 只要求"如实说明没查到、口语化"——「要不要查其他时间段」是 LLM 在口语化要求下**自由发挥**的跟进提议
2. 这句话随 `type: "answer"` 事件发出，**不是 `type: "ask"` 事件**。wrapper 的状态保留逻辑是 `keep_state = 存在 ask 事件`（app.py `run_xxx_graph`）→ 全是 answer → **`session_state.clear()`，会话状态被清空**
3. 用户回「可以」时已无活跃状态 → `classify_intent("可以")` 低于所有阈值 → `other` → 八个业务域分支全不匹配 → **else 掉进旧 InfoDoubleCheckPipeline** → 意图节点判「无法回答」→ [reactive_pipeline.py:197-201](../graph/reactive_pipeline.py#L197-L201) 输出兜底「对不起，我目前掌握的能力无法解决你的问题」

用户视角是"bot 在等我确认"；系统视角是"回答已完毕，会话结束，『可以』是个全新的无意义问题"。

**更深一层**：即使状态保留下来「可以」也走不通——各 handler 的 `handle_reply` 处理的是"缺参数追问"场景（`missing_params` 非空），而这里是查询**已完成**后的续聊提议，状态机里没有"等待确认继续（pending continuation）"这个状态。不是"状态被清了"一个 bug，是**"查询后跟进提议"这个交互模式整个没被设计过**。

### 修复方向（待拍板）

| 方案 | 做法 | 说明 |
|---|---|---|
| **A（止血，建议先做）** | 各域 `_llm_format_*_result` 的 prompt 明确禁止：「数据为空时只说明没有数据，**不要建议查询其他时间段**」 | 一行改动，消灭协议外的承诺；8 个域的格式化 prompt 都要过一遍 |
| **B（正解）** | 空结果时 graph 显式发 ask 事件：「今天没查到告警，要查其他时间段吗？近三天 / 近一周 / 近一个月」——复用 vague 模式，状态保留 | 需同时处理「可以」→ 确认默认选项的语义映射（确认词解析，可参考案例 6 的序数/选项拦截） |
| C | LLM 回答以问句结尾时保留状态，下一轮短确认词结合上一轮回答处理 | 工程复杂度高，暂不建议 |

建议 A 先上，B 作为后续正解（A+B 组合最稳）。

### 教训

- **LLM 的自由文本越过协议层承诺能力 = 必然失约**：凡是 LLM 生成给用户的话，其中"提议/追问/确认"类内容要么被 prompt 禁止，要么落成显式的 ask 事件，二者必居其一
- **会话状态的生杀判定是 `ask` 事件，而 LLM 的话不在协议里**——review graph 输出时要把"LLM 回答里出现问号"当成一种告警信号
- 排查这类问题时先认兜底话术的"出处"：「对不起，我目前掌握的能力无法解决你的问题」出自旧 pipeline，说明该轮**根本没进任何态势域**；不同兜底话术对应不同的掉落层级

## 案例 8：查询完成后省略式追问「昨天呢」掉兜底

**日期**：2026-09-15
**状态**：已修复——「done 状态保留 + 拼接重分类」（app.py）

### 现象

```
用户：今天食堂的菜谱是什么？
bot：没有查到今天的菜谱数据。
用户：昨天呢
bot：对不起，我目前掌握的能力无法解决你的问题
```

### 根因：上下文继承只覆盖「追问态」，不覆盖「已完成态」

1. 第一轮走食堂域新意图分支，graph 出了答案、全程无 `ask` 事件 → `run_canteen_status_graph` 尾部 `keep_state=False` → **`session_state.clear()`，状态被清空**。查询完成即上下文归零
2. 第二轮「昨天呢」：`active_state` 为 None → 跳过情况 1 追问分支；`classify_intent("昨天呢")` —— 三个字的省略句与任何域的中心向量相似度都低于 0.65 阈值 → `other`；elif 链全不匹配 → 掉进旧 InfoDoubleCheckPipeline → [reactive_pipeline.py:197-201](../graph/reactive_pipeline.py#L197-L201) 输出兜底（**与案例 7 同一掉落层级**）
3. 已有的多轮逻辑（情况 1 `handle_reply`、情况 1.2 追问态新意图接管）处理的都是「系统追问缺失参数、等待用户补充」场景；「查询完成后用户换个时间再问」这个交互模式同样没被设计过——与案例 7 的结论呼应：**状态机的生杀判定只有 ask 事件，answer 即结束**。embedding 分类器对省略句天然无能为力（省略句必须靠上下文补全），所以两头的中间地带就掉兜底了

### 修复（本次实施）

**思路**：查询完成后不清状态，标记 `done=True` 留作「省略式追问」的上下文；本轮识别不出意图时，拼接上一轮问题重新分类。

1. **各 `run_xxx_graph` 尾部（10 个域对称修改）**：查询结束（无 ask 事件）不再 `session_state.clear()`，改为 `state.done=True`、`missing_params` 清空后继续保留，靠 `SessionStateManager` 的 300 秒超时自动过期。图内不读输入侧 `done` 字段，保留状态不会被图误用
2. **路由入口**：用 `is_waiting`（有状态且 `not done`）区分「追问态 / 已完成态」——追问分支判定不再被完成态污染；完成态轮次正常跑意图分类
3. **新增情况 1.5**：`top_intent == other` 且存在 done 状态 → 用上一轮 `original_query` 拼接本轮输入（`"今天食堂的菜谱是什么？ 昨天呢"`）重新 `classify_intent`；命中业务域则 `start_module_flow` 按全新流程执行——`extract_slots` 从拼接句能正确抽到「昨天」（`parse_time_slot` 手工段「昨天」判断在「本周/本月」之后，拼接句不含那些前置词，不会误命中「今天」）；仍未命中则掉原有 pipeline，行为与之前完全一致
4. **链式追问天然支持**：拼接命中的新状态 `original_query` 即拼接句，再问「那前天呢」继续拼接

**验证要点**（容器内重启后）：
- 「今天食堂的菜谱是什么？」→「昨天呢」应走食堂域查昨天菜谱，app.log 可 grep `[省略式追问]`
- 追问态（缺参数被追问时）回复「昨天」仍走情况 1 `handle_reply`，行为不变
- 查询完成后输入全新问题（能命中某域 / 纯闲聊）行为不变

### 已知边界

- 5 分钟窗口内，完成态之后的任何 `other` 输入都会先尝试拼接——拼接不命中就掉旧 pipeline，只是多一次分类调用；命中才分流
- 完成态常驻 `session_state.states` 一条记录直到超时，量级可忽略

### 教训

- **「状态清空 = 上下文归零」**：查询完成后立刻 clear，意味着系统主动放弃了多轮会话能力；凡是有多轮语义的对话，完成后应留「最近意图」残迹（带超时），而不是等用户省略追问时无迹可循
- **分支条件要把「状态存在」细化为「状态存在且在等回复」**：否则保留状态的新逻辑会污染追问分支
- 与案例 7 合并看：会话状态机只有「追问中 / 无状态」两态，「查询已完成但可续聊」是长期缺失的第三态，本次补上（done 态）

## 案例 9：MCP 服务端恢复后，域查询仍报「工具未加载」（懒加载缓存投毒）

**日期**：2026-09-16
**状态**：已修复——方案 1 已实施（11 域统一：空工具不入缓存 + 明确错误事件，下次查询自动重试）

### 现象

综合态势域查询报 `overview:getBasicInfo 工具未加载`。但此时 Java 侧 overview 服务**已经恢复**，工具名（`overview:getBasicInfo` / `overview:getDeviceHealth`）与 `_JAVA_TOOL_MAP` 完全一致——服务端、工具名、映射三者都对，就是加载不到。

### 根因：懒加载只掷一次骰子，空图也被永久缓存

app.py 各域统一的懒加载模式：

```python
if _xxx_graph is None:                    # 该域第一次被问到时才初始化
    tools = await load_xxx_tools()        # 后端不可用 → 返回 {}
    _xxx_graph = build_xxx_graph(tools)   # 空图正常编译、正常缓存，永不重试 ❌
```

实测时间线（app.log）：

```
14:23:37  首条 overview 查询进来 → 懒加载恰逢 overview server 不可用
          → WARNING: MCP server [overview] 工具加载失败，跳过
          → WARNING: 未找到任何综合态势总览 MCP 工具 → 空图入缓存 ❌
14:25/14:26  再问 → 缓存命中空图 → 「工具未加载」
14:27:54  另一域（消防）首次初始化触发新一轮加载 → 11 个 server 全部成功
          （overview 加载到 2 个工具）——但 overview 缓存已中毒，与它无关
```

即：**该域首次查询撞上后端临时不可用 → 该域缓存死锁直到重启**，之后 Java 端恢复与否不再有影响。触发点是"该域第一条查询"的时机，不是前端/服务启动动作——前端启动只是把第一条查询送了进来。全部 11 个域共用同款 `if _xxx_graph is None: build` 模式，人人有份。

### 排查思路

1. 「工具未加载」只作为 ws error 事件发给前端，graph 里没有 logger、**不进 app.log** → 直接 grep 不到，要从 server 端加载日志入手
2. 案例 1 加的容错 loader 分级日志是关键证据：对比两个时间点——14:23 `overview 工具加载失败` vs 14:27 `overview 加载到 2 个工具`，服务端恢复但用户仍报错 → 指向"缓存未刷新"
3. `grep -ao "overview:get[A-Za-z]*" app.log | sort -u` 确认注册工具名与映射一致，排除案例 4 那类命名不匹配

### 修复方向（待拍板）

| 方案 | 做法 | 说明 |
|---|---|---|
| **1（推荐）** | 11 个域统一改：`get_xxx_graph()` 懒加载时 tools 为空**不缓存**，`run_xxx_graph` 检测到空图发「MCP 工具暂时不可用，请稍后再试」error 事件；下次查询自动重试加载 | 机械改动约 22 处（11 域 × 懒加载块 + run 包装），一次排掉全部域的雷；空判断同时覆盖"加载失败"与"工具名不匹配"两种空 |
| 2 | 只改 overview 域 | 治标，其余 10 个域留着同样的雷 |

临时恢复：重启 Python 服务（缓存重建时 server 已在线，自然带上工具）。

### 修复（本次实施，方案 1）

1. **各域 `get_xxx_graph()`（11 个对称修改，app.py）**：`load_xxx_tools()` 返回空时 `logger.warning`（「xxx MCP 工具为空，本次不编译图」）并 `return None`——不再把空图写入模块级缓存，下次查询重新走懒加载自动重试
2. **各域 `run_xxx_graph()`（11 个对称修改，app.py）**：`graph is None` 时向前端发 `type: "error"`「MCP 工具暂时不可用，请稍后再试。」，并把会话状态按**完成态**保留（`done=True`、`missing_params` 清空）——沿用案例 8 的完成态约定，不污染追问分支；用户下轮再说「现在园区有多少设备」或省略式追问，都能重新进域并触发重试
3. 空判断 `if not tools` 同时覆盖两种空：加载失败返回 `{}`、工具名全不匹配被过滤光（案例 4 那类），后者也会得到明确报错而非死缓存

**验证要点**（容器内重启后）：
- 停掉某域对应 Java 服务再问该域 → 前端收到「MCP 工具暂时不可用，请稍后再试」，app.log 有「xxx MCP 工具为空，本次不编译图」
- 服务恢复后**不重启 Python** 再问同一域 → 应正常出数（重试生效）
- 注意：本次已中毒的 overview 缓存是旧代码留下的，改代码不会清它，**仍需重启一次 Python 服务**

### 教训

- **懒加载初始化是一次性时机赌博**：首个查询撞上后端在线，缓存就是好的；撞上离线，该域死到重启。任何"首次使用时初始化并永久缓存"的结构，都要回答"初始化失败了怎么办、什么时候重试"
- **空图也是图**：`build_xxx_graph({})` 不报错、正常响应，坏得非常安静——入缓存前要对关键依赖做空校验
- **域级错误事件只走 ws 不进日志**：排查时以 loader 的分级日志（案例 1）为准；重要错误分支建议同时 `logger.warning`，否则日志里出现断层

## 案例 10：「今天园区能耗情况怎么样？」掉兜底（语料薄 + 泛句式无锚）

- **贴阈值分数（0.63~0.66）是最危险的区间**：看似「差一点」，实际是语料覆盖缺口；靠下调阈值硬救会把脏查询放进来

## 案例 11：省略式追问「昨天呢」查对了数据，回答却说「今天」

**日期**：2026-09-18
**状态**：已修复——各域 LLM 整理 prompt 增加「本次查询的时间范围」锚（13 个 graph 对称修改 + slots.py 新增 format_query_time）

### 现象

```
用户：今天食堂的菜谱是什么？
bot：没查到今天（2026-09-18 周五）的菜谱，返回的数据是空的。
用户：昨天呢
bot：今天没有查到食堂菜谱数据。
```

查询实际查的是昨天，回答却按「今天」表述。与案例 8 同一入口，但案例 8 修复后掉兜底问题已不存在——这次是**回答生成环节**的锅。

### 根因：情况 1.5 的 original_query 约定与 LLM 整理 prompt 的信息缺口

1. 案例 8 的省略式追问修复里，「昨天呢」经拼接重分类命中食堂域后按继承式启动：槽位只用本轮输入抽取（date=昨天 ✅ 查询是对的），但 **original_query 固定传首轮原话「今天食堂的菜谱是什么？」**（防连续追问拼接串滚雪球——这个约定本身是对的）
2. 问题在消费端：各域 `_llm_format_*_result` 的整理 prompt 里，LLM 能看到的「用户意图」信息只有 `用户查询类型` 和 `用户原话：{original_query}`，外加 `今天日期`。**slots 里真实查询的时间范围从没进过 prompt**
3. 于是整理 LLM 面对空数据时，用「用户原话（今天食堂的菜谱…）+ 今天日期」组织回答 → 「今天没有查到食堂菜谱数据」。它不是读错了数据，是**没人告诉它本次查的是昨天**

注：`_compact_week_menu` 内部按 `date.raw`（昨天→周四）过滤整周菜谱是独立小实现，查询口径一直正确；翻车只发生在「把结果说给人听」这一步。

### 修复（本次实施）

## 案例 12：时间澄清追问「近几天」，用户答「今天」被误回「没太理解」

**日期**：2026-09-18
**状态**：已修复——slots.py 新增 `parse_point_day`，10 个 handler 的 `_pending_date_clarify` 分支对称接入点日解析

### 现象

```
用户：最近发布了哪些信息？
bot：您想查询近几天的信息发布数据？可以直接回复具体天数，
     例如"近两天"、"近四天"，或选择：近三天、近一周、近一个月
用户：今天
bot：没太理解，请说具体天数，例如"近两天"、"近四天"，或选择：近三天、近一周、近一个月
```

### 根因：澄清分支只认「区间」句式，不认「具体一天」

是逻辑问题，且是案例 6 教训的复刻——**bot 列出选项，就要预期用户不按选项原文回答**：

1. 「最近发布了哪些信息？」→ `parse_time_slot` 命中 vague 模式（「最近」）→ graph `vague_date` 发 ask、状态标记 `_pending_date_clarify`
2. 用户答「今天」→ `handle_reply` 澄清分支。该分支的解析器只覆盖三类：`近N天` 正则、`三天/一周(周)/月` 关键词、序数选择（部分域）——**「今天/昨天/前天」这类点日说法不在其中**
3. `start` 为 None → re_ask「没太理解」。讽刺的是 ask 话术让用户「回复具体天数」，用户给了个更明确的一天，系统反而接不住

这与 `parse_time_slot` 主流程形成对比：主流程能认「今天/昨天/前天」（手工段+jionlp），只有澄清分支这套独立小解析器没覆盖——同一概念两套口径的又一例。

### 修复（本次实施）

1. **slots.py 新增 `parse_point_day(query)`**：解析「今天/今日/当天」「昨天/昨日」「前天」，生成与 `parse_time_slot` 手工段同构的 `{span, start, end, raw}` 结构；未命中返回 None。不含明天/后天（澄清选项都是历史区间，未来时间由各图 future 分支拒绝）
2. **10 个 handler 的澄清分支对称接入**（person/vehicle/security/canteen/information/energy/meeting/fire/perimeter/twins）：在拒绝判定之后、区间解析之前先试点日解析，命中则回写 `slots.date`、清 `_pending_date_clarify`/`_date_options`、`action=continue` 重跑图
3. 序数改写（fire/perimeter/twins 的 `parse_ordinal_choice`）不受影响：改写后的 q 是「近三天」类区间文案，`parse_point_day` 返回 None 自然落回区间解析

### 验证要点（容器内重启后）

- 「最近发布了哪些信息？」→「今天」：应直接查今天并出数，不再 re_ask；日志 graph input 里 `slots.date.raw=今天`
- 同款流程答「昨天」「近四天」「近一周」「第一个」：行为各自正确（点日/区间/序数互不干扰）
- 澄清后答无关内容（「你好」「算了」）：仍走原 re_ask / give_up，不被误判成「今天」——`parse_point_day` 只认点日词，无 `parse_time_slot` 那种「兜底默认今天」的误吸风险

### 教训

- **追问话术圈定的答案空间 ≠ 用户实际会答的空间**：问「近几天」答「今天」是完全合法的回答；澄清解析器的覆盖面必须 ≥ 话术暗示的范围 ∪ 常见省略回答
- **同一概念（时间解析）存在多套实现时，修主流程不会自动修到分支**：`parse_time_slot` 会认「今天」，澄清分支自己那套小解析不会；能用同一个函数就不要维护两份口径

## 案例 14：追问态回复「不用了」取消后，前端永久转圈、无法继续发消息

**日期**：2026-09-18
**状态**：已修复——give_up 分支补发 done 事件

### 现象

```
（时间澄清追问中）
用户：不用了
bot：好的，已取消查询。请问您还有其他问题吗？
（此后前端加载指示永久转圈；再发消息输入框也不响应）
```

### 根因

后端 `handle_reply` 命中 DECLINE_KEYWORDS 返回 `action=give_up`，app.py 的 give_up 分支只发了
`{"type": "answer"}` 就 `continue`，**没有发结束标记 `{"type": "done"}`**。

前端的回合生命周期（web/js/app.js）：

- 发消息时置 `turnActive = true`：显示转圈指示、`sendBtn.disabled = turnActive`（**发送按钮被禁用**）
- `turnActive` 只在 `finishTurn()` 里复位，而 `finishTurn` 仅由 `done` / `ask` / `error` 事件触发
- **`answer` 事件不结束回合**（它按流式分块设计，只追加文本）

所以只发 answer 不发 done 的后果是：转圈永不消失 + 输入框永久锁死（placeholder 显示「助手正在回复…」）。
「发消息也不会动」不是后端卡住，是前端整个回合被协议缺口锁住了。所有 graph 路径（finalize、
give_up、future_date、unsupported_date 等节点）都以 done 收尾，只有这个手写分支漏了。

### 修复

app.py give_up 分支（情况 1.1）在 answer 之后补发 done 事件，对齐 graph 约定：

```python
await websocket.send_text(json.dumps({
    "event": "custom",
    "data": {"type": "answer", "content": result["answer"]}
}, ensure_ascii=False))
# answer 之后必须补 done：前端收到 done 才收起加载指示、解锁输入框
await websocket.send_text(json.dumps({
    "event": "custom",
    "data": {"type": "done"}
}, ensure_ascii=False))
```

排查时已核对全部裸发事件点：re_ask 分支发 `ask`（前端 ask 自带 finishTurn，正确）；
接管路径走 `start_module_flow`（完整流程，含 done）；run_*_graph 内 MCP 不可用的 error 事件
（前端 error 也触发 finishTurn，正确）——只有 give_up 这一处漏发。

### 验证要点（容器内重启后）

- 时间澄清追问中回「不用了」：出现「好的，已取消查询」后转圈应立即消失、输入框恢复可用
- 取消后紧接着发「今天园区有多少人」：应正常走新查询（会话状态已 clear，走全新分类）
- 回归：连续不相关超阈值的 give_up（「看起来您可能不想继续查询了…」）同样不再卡死
- 回归：re_ask 追问（「没太理解，请说具体天数…」）行为不变（ask 事件本来就结束回合）

### 已知边界

- 连接建立阶段的 pipeline 创建失败路径（app.py 1543/2216/2239）发的是裸 `{"type": "error"}`
  （无 event=custom 包装），前端 switch 按 `data.event` 分发收不到，靠紧随的 `websocket.close()`
  触发断连兜底——属遗留格式，不在本例范围，暂不动

### 教训

- **协议约定靠约定没有约束力**：done 事件是前端回合生命周期的唯一可靠复位点，任何手写发送
  分支都必须「answer 必配 done」。graph 路径靠节点收尾天然满足，app.py 里绕过图的分支要逐个核对
- 前端「卡死 + 不能发消息」先查 `turnActive` 复位链路（哪些事件触发 finishTurn），再查后端
  是否发了对应事件——本例后端其实早就回完话了，是回合没被关闭

## 案例 15：取消后答「没有了」，被回「对不起，我目前掌握的能力无法解决你的问题」

**日期**：2026-09-18
**状态**：已修复——新增收尾语拦截分支（情况 1.4）

### 现象

```
用户：出去了多少
bot：（车辆态势出数）
用户：昨天呢
bot：当前平台后端仅支持查询今日数据，是否为您展示今日离开人数？
用户：不用了
bot：好的，已取消查询。请问您还有其他问题吗？
用户：没有了
bot：对不起，我目前掌握的能力无法解决你的问题   ← 生硬
用户：我说没有了
bot：对不起，我目前掌握的能力无法解决你的问题   ← 还是生硬
```

### 根因（不是报错，是「未识别意图」的标准兜底）

1. 「不用了」走 give_up，`session_state.clear()` **清空会话状态**（设计行为，案例 14 已把该分支收口）
2. 「没有了」进来时 `active_state = None` → 走情况 2 全新分类：`classify_intent("没有了")`
   低于所有业务域阈值 → `other`
3. 情况 1.5 省略式追问要求 `active_state is not None and active_state.done` → 跳过；
   十三个业务域 elif 全不匹配 → 掉进最后的旧 pipeline（InfoDoubleCheckPipeline）→
   意图节点判「无法回答」→ [reactive_pipeline.py:200](../graph/reactive_pipeline.py#L200)
   输出兜底「对不起，我目前掌握的能力无法解决你的问题」

即：**整条链路按设计运行，但对「还有其他问题吗」的否定回答被当成了待分类的新查询**。
这句话的真实语义是对开放问题的礼貌收尾，任何业务域都不该接、也不该回「无法解决」。

### 修复

app.py 新增收尾/告别语整句识别，在意图分发前拦截（情况 1.4，排在情况 1.5 之前）：

1. `_CONVERSATION_CLOSE_RE` + `is_conversation_close()`（MODULE_HANDLERS 前定义）：
   整句匹配（允许「我说」「就是」等口头铺垫、「没有了谢谢」这类后置致谢、
   吧/啦/呀 等语气尾），核心词：没有了/没了/没有/不用了/暂时没有/再见/拜拜/谢谢/辛苦了/好的；
   **长度上限 12 字 + 收尾字符类闭合**，保证「没有告警吗」「没有什么新闻」这类
   真查询不会被误吞（尾字不在字符类里，整句匹配失败 → 照常走分类）
2. 新分支 `elif top_intent == "other" and is_conversation_close(query)`：
   回「好的，如需查询园区相关数据随时找我。」+ done 后 continue
   （answer 必配 done，案例 14 的教训）

两个顺序细节：

- **只拦 `top_intent == "other"`**：追问态（is_waiting）时 top_intent 为 None，不进本分支，
  追问中的「不用了」仍由 handler 的 DECLINE_KEYWORDS 处理（取消当前任务），语义不变
- **排在情况 1.5 之前**：否则 done 态下「没有了」会被拼接上轮问题重新分类，
  把已完成的查询再执行一遍（附带修掉这个潜在的重查问题）

### 验证要点（容器内重启后）

- 复现路径：…「不用了」→「好的，已取消查询。请问您还有其他问题吗？」→「没有了」
  → 应回「好的，如需查询园区相关数据随时找我。」；再「我说没有了」同样礼貌收尾
- 取消后直接问新查询（「今天园区有多少人」）：不受影响，照常分类进域
- 追问态回归：时间澄清中回「不用了」仍走 handler 取消（give_up 话术），不被新分支抢先
- 真查询不误吞：「没有告警吗」「没有什么新闻」「没有别的了吗+具体业务问句」照常分类
- 完成一轮查询后（done 态）单独发「没有了」：应礼貌收尾，**不再重新执行上轮查询**
- 前端收口：收尾回复后转圈正常消失、输入框可用（answer+done 配对）

### 已知边界

- 兜底话术分层未变：这句话出自旧 pipeline，说明该轮没进任何态势域（案例 7 教训）；
  收尾语只是众多「会掉 old pipeline 的输入」里被识别的一类，其余闲聊仍走原兜底
- 「嗯」「哦」等单字应答未纳入收尾语（歧义大、收益小），单独发仍走原兜底
- 收尾语判定是正则整句匹配，覆盖常用说法；更长/更花哨的表达（如「暂时没想到要查啥了」）
  不命中，维持原兜底——可按实际语料逐步扩充核心词

### 教训

- **系统主动发起的开放问题（「还有其他问题吗」）必须预算到用户的否定回答**：
  问出去的话术决定了下一轮输入的语义，回答路径要跟问话术成对设计
- 兜底话术是排查的路标：不同兜底文本对应不同掉落层级（旧 pipeline / 域内
  unsupported / 工具失败），先认话术出处再查链路

## 案例 16：案例 13 的日期校验误伤「今天」——「今天园区能耗情况怎么样？」被兜底拒绝

**日期**：2026-09-20
**状态**：已修复——`_is_supported_energy_date` 改为语义判定 + 双保险

### 现象

```
用户：现在园区有多少人？        → 出数
用户：今天园区能耗情况怎么样？   → 当前后台仅支持查询今天或今年的能耗数据，其他时间范围暂时查不到。  ❌
用户：今天的                   → 正常出数 ✓
```

「今天」明明在支持范围内，却被 案例 13 新加的 unsupported_date 兜底拦下了。

### 根因

`_is_supported_energy_date` 的日期计算只认一种形状：`start.date() == end.date() == 今天`。

日志证实两轮输入都判到 `overall_energy`，差异只在日期槽形状：

- 「今天的」→ jionlp 解析出的形状过了校验 → 放行出数
- 「今天园区能耗情况怎么样？」→ jionlp 对整句解析出的形状没过校验 → unsupported_date

即**同一语义、不同句子，jionlp 解析出的时间跨度形状不一致**（疑似 `[今天00:00, 次日00:00)`
左闭右开、或其他无法 `fromisoformat` 的格式；jionlp 只在容器里有，本机无法复现其确切输出）。
校验按形状硬卡，形状稍有出入就误伤。

另注意：jionlp 分支的 `raw` 存的是**整句原话**（slots.py `parse_time_slot` 第 2 段 `"raw": query`），
不只是时间词本身——这既是坑（原话里含「今年」两个字也可能误放行）也是机会（原话里明确说了
「今天」就可以直接信任语义）。

### 修复

[energy_status_langgraph.py](../graph/energy_status_langgraph.py) `_is_supported_energy_date` 改为语义判定 + 双保险：

1. **原话语义优先**：raw 含「今天/今日/当天」直接放行（今年类词汇原有逻辑保留）
2. **日期计算兜底且放宽边界**：起点在今天、终点在今天或次日零点（左闭右开写法）；
   起点为当年 1 月 1 日、终点不越过次年 1 月 1 日
3. `fromisoformat` 前统一 `str()`，None/异常格式都走 False

### 验证要点（容器内重启后）

- 新会话直接问「今天园区能耗情况怎么样？」：应正常出数（修复前被兜底）
- 「昨天呢」（紧随其后）：仍应兜底「仅支持今天或今年」（回归 案例 13）
- 「上周的能耗」「近三天的用水量」：仍应兜底
- 「今年能耗」「年度用电」：放行出数
- 「今天的」（省略式追问）：仍正常出数
- 有条件的话看一眼日志/print：`parse_time_slot("今天园区能耗情况怎么样？")` 的真实形状，
  确认误判点（本机无 jionlp，未能留存证据）

### 已知边界

- raw 是整句原话，原话里顺带提到「今天」也会放行（如「上周和今天比呢」——后端本就只有
  今天数据，放行只是回到「答非所问范围」的老问题，不会比之前更差）
- jionlp 的确切输出形状仍未实证（本机无 jionlp），修复以语义为准不依赖形状，若后续仍有
  误伤，按验证要点留日志证据再收窄

### 教训

- **在同一语义的不同表述间，解析器的输出形状可能不一致**；对解析结果做白名单校验时，
  卡形状必误伤，应回到语义层（原话说了什么）做判定
- 加了校验的路径要立刻回归「合法输入」用例：案例 13 只验证了该拒绝的被拒绝，
  没重测该放行的（今天）是否仍放行——校验类改动必须正反两侧都回归

## 案例 16：能源查「今天」被误回「仅支持查询今天或今年」

**日期**：2026-09-20
**状态**：已修复——`_is_supported_energy_date` 改按语义判定、容忍解析形状差异

### 现象

```
用户：今天园区能耗情况怎么样？
bot：当前后台仅支持查询今天或今年的能耗数据，其他时间范围暂时查不到。   ← 案例 13 的兜底误伤了今天
（同会话紧随）用户：今天的
bot：（正常出数）
```

日志证据：11:22:03 整句查询走了 unsupported；11:22:31 省略式「今天的」→ 情况 1.5 →
call_tool → LLM 出数。**同为「今天」语义，整句被拒、短输入放行**。

### 根因

案例 13 的 `_is_supported_energy_date` 只认「起止日期都在今天」这一种形状：

```python
if s.date() == today and e.date() == today:   # 整句解析出的跨度形状对不上就误杀
    return True
```

「今天」的日期槽由 jionlp 原生解析产生（slots.py 手写规则不处理今天），jionlp 对
「今天园区能耗情况怎么样？」与「今天的」给出的时间跨度形状不一致——前者大概率是
`[今天00:00, 次日00:00)` 这类区间上界写法（或无法 fromisoformat 的格式），终点落在了
次日 → 判 False → unsupported。jionlp 只装在容器里，本机无法复现其确切输出，故修法
不依赖具体形状。

### 修复

`_is_supported_energy_date`（[energy_status_langgraph.py](../graph/energy_status_langgraph.py)）改按语义双保险：

1. **原话捷径**：`raw` 含「今天/今日/当天」直接放行——jionlp 分支的 raw 存的是整句
   原话，明确说了今天就不看解析形状；「今年/本年/年度/全年」捷径原已有
2. **日期计算兜底放宽**：今天 = 起点在今天、终点在今天**或次日零点**（左闭右开写法）；
   今年 = 起点 1 月 1 日、终点不越过次年 1 月 1 日

### 验证要点（容器内重启后）

- 「今天园区能耗情况怎么样？」：直接出数，graph input `query_type=overall_energy`
- 「昨天呢」/「上周呢」/「近三天的用水」：仍走兜底回答（raw 与日期计算都不过）
- 「今年的用电排名」「2026 年能耗」：放行
- 省略式「今天呢」「今天的」：出数（回归）

### 教训

- **对第三方解析器的输出形状不要假设唯一**：同一个词在整句和短句里可能解析成不同的
  跨度形状；校验逻辑要按「用户说了什么」而不是「解析器算出了什么」来定
- 日志里同会话的一过一拒是最强线索：先找差异（输入长度→解析分支），再下结论

## 案例 17：进入人数问完问「出去得呢」，回答还是进入人数

**日期**：2026-09-22
**状态**：已修复——子类型继承加兜底值保护 + 人员域补省略式正则

### 现象

```
bot：当前平台后端仅支持查询今日数据，是否为您展示今日进入人数？
用户：好的
bot：今天园区进入人数为 456 人。        ← 正确（案例 11 补充修复生效）
用户：出去得呢                           ← 省略式追问且换了子类型（进入→出去）
bot：今天园区进入人数是456人。           ← ❌ 还是进入
```

### 根因（两个叠加）

1. **情况 1.5 子类型继承无条件覆盖**（案例 13 引入的缺陷）：继承逻辑是
   `slots[k] = active_state.slots[k]`——只要上轮有子类型就压给本轮。案例 13 的场景
   （「昨天呢」）里本轮 fresh 抽取落兜底值，覆盖无感；但「出去得呢」是在省略式追问里
   **明确换子类型**，fresh 即便抽对了也会被上轮的 `enter` 覆盖。与追问态 handle_reply
   「子类型已定不被覆盖」的既有语义也不一致
2. **人员域离开正则缺口**：leave 分支全是「动词+多少/几/人数」句式，
   「出去得呢 / 出去呢 / 离开呢」这类**动词+语气词**的省略式说法一个都匹配不到，
   fresh 抽取落 `count` 兜底 → 即使没有问题 1，也会按继承走到 enter

### 修复

1. **app.py 情况 1.5 ③**：新增 `_SUBTYPE_FALLBACKS`（与 slots.py 各抽取器初始值对齐：
   `query_type` → count/basic_info/device_list；`event_type` → count/alarm_list/
   week_menu/info_view），继承改为**仅当本轮 fresh 抽取为空或落在兜底值**才继承，
   本轮明确抽出具体子类型时以本轮为准
2. **slots.py 人员域**：enter/leave 正则各补一条句尾省略式
   `(?:那|再|就)?(?:出去|离开|离园|走了?)[的呢了吧得呀哦嘛]{0,3}$`（enter 对称补
   进入/进来/入园/来了），覆盖「出去得呢」「那出去呢」「出去了呢」「离开呢」等说法

### 验证要点（容器内重启后）

- 复现路径：进入人数确认出数后问「出去得呢」→ 应回答**离开/出去**人数（不再是 456 进入）
- 「出去呢」「出去的呢」「那离开呢」：同上
- 回归 案例 13：「今天园区能耗情况怎么样？」→「昨天呢」仍正确落入能源 unsupported；
  食堂「昨天呢」仍查菜谱；「昨天的人员告警呢」等完整问句不受影响
- 回归省略式继承：「那上周呢」（不带子类型信息）仍继承上轮子类型
- 前端正常收口（answer+done 配对）

### 已知边界

- `device_list`（设备查询）、`basic_info`（综合总览）既是抽取器兜底值也是合法显式
  子类型：显式问「设备列表」而上一轮是「设备详情」时，fresh 的 device_list 仍会被
  继承覆盖成 device_detail——除非抽取器能区分「默认值」和「显式命中」，否则无解，
  暂按罕见输入接受
- 省略式正则只补了人员域（enter/leave），其他域若出现同类「动词+语气词」省略式
  （如「告警呢」在安防域的表现）按语料逐域补
- 追问态 handle_reply 的 event_type 合并对兜底值没有同样的保护（仅 query_type 有），
  属历史行为，未动

### 教训

- **继承规则必须同时设计「本轮明确换类型」的出口**：写「继承上轮」时先问一句——
  本轮输入如果明确表达了不同子类型怎么办？只测试「昨天呢」式输入会漏掉「出去呢」式输入
- 修 A 领域（能源子类型继承）时想到的规则，直接泛化到所有域前，要过一遍各域的
  典型省略式说法；泛化规则的反例往往藏在别的域里
