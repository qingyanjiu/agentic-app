## 二、延迟与性能优化

### OPT-P01 启动预加载意图识别模型（已实施）

- **问题**：`SentenceTransformer` 首次加载需要数秒，第一个用户会额外等待模型初始化。
- **做法**：FastAPI startup 事件里 `await get_classifier()` 提前完成全局单例初始化；模型加载、`encode` 和相似度计算都通过 `loop.run_in_executor` 放到线程池，避免阻塞 Uvicorn 事件循环导致 WebSocket 卡顿。
- **效果**：首个请求不再承担模型加载时间；文档未给具体秒数。
- **位置**：`app.py:121`、`agent/intent/classifier.py:4029`；《架构文档》§4.1、§5.2。

### OPT-P02 启动后台预热场景 MCP 与 13 个业务域图（已实施）

- **问题**：第一个用户要支付两类冷启动成本——场景 MCP 的 `initialize + tools/list` 握手，以及 13 个业务域各自加载 MCP 工具并编译图（单域工具加载外层超时 15s）。
- **做法**：`startup()` 调 `_start_prewarm()`，用 `asyncio.create_task` 在后台并发跑两个任务：
  - `_prewarm_scene_mcp()`：先建场景图，再 `list_tools()`（8s 超时）把握手和工具列举一次付清；
  - `_prewarm_business_graphs()`：按 `_BUSINESS_GRAPH_GETTERS` 逐个调用 13 个 `get_*_graph()`，图编译后落模块级缓存。
  每个域独立 try/except，单个失败只告警；`PREWARM_ON_STARTUP=0/false/off/no` 可整体关闭。
- **效果**：首个场景指令不再等握手，首个业务查询不再等工具加载；未量化。
- **位置**：`app.py:1772-1802`；《架构文档》§4.1、《UE场景控制接入说明》§8.3。

### OPT-P03 懒加载 + 模块级图缓存（已实施）

- **问题**：`get_mcp_tools()` 每次调用都会新建连接；如果每个请求都加载工具并编译图，延迟和资源开销都不可接受。
- **做法**：13 个业务域各自维护模块级 `_xxx_graph = None`，首次 `get_*_graph()` 时加载工具、编译图，之后整个进程复用同一张编译好的图，MCP 工具连接也随之复用。
- **效果**：每个域在一个进程内只连一次 MCP、只编译一次图。
- **位置**：`app.py:188` 等 13 处；《架构文档》§4.2、§7.5。
- **配套约束**：空工具不入缓存，见 OPT-S03。

### OPT-P04 业务回答逐 token 流式输出（已实施）

- **问题**：13 个业务图的回答节点原来用 `await llm.ainvoke(prompt)`，必须等整段生成完才把 `answer` 事件发给前端，首字延迟等于整段生成时间。
- **做法**：
  - 新增 `graph/stream_utils.py::stream_llm_text()`，内部用 `llm.astream()`，每个 chunk 以 `{"type":"answer","content":...}` 通过 LangGraph custom 通道推出，同时累积成完整文本返回；
  - `app.py::_stream_graph_to_ws()` 用 `graph.astream(graph_input, stream_mode=["custom","values"])` 跑图：custom 的 answer chunk 立即 `send_text`，values 的最后一个快照作为 `final_state`；
  - `streamed_answer=True` 时，收尾转发 `events` 跳过完整 answer，避免前端显示两遍；
  - 流式中途失败但已有内容 → 返回已生成部分；一个 token 都没拿到才抛给外层，由 `_llm_format_*` 降级为 `raw_text`；
  - 没有 writer 的场景（单测直接调用格式化函数）退化为纯累积，结果不变。
- **效果**：前端首字从“整段生成完”变为“首个 token”；未量化毫秒数。
- **位置**：`graph/stream_utils.py:42`、`app.py:154`、13 个业务图；《架构文档》§7.6。

### OPT-P05 场景规则快通道（已实施）

- **问题**：场景指令的耗时主要在两处——先读 `get_scene_state` 快照（一次 MCP 往返），再把工具清单 + 快照 + 原话交给 LLM 选工具（一次大模型调用）。切楼层、重置视角这类确定性指令完全不需要大模型。
- **做法**：`plan_action` 调 LLM 前先跑 `_fast_plan()`，复用规则兜底 `_rule_based_plan()`；命中则直接产出 `{tool, arguments}`，不调 LLM。命中条件：
  1. 非追问轮（`ask_count == 0` 且无 `last_question`）；
  2. 非复合句（排除“然后/再/并且/同时/顺便/之后/逗号/分号”）；
  3. 规则能给出明确工具且不需要追问；
  4. 工具在 `_FAST_PATH_TOOLS` 白名单内（14 个确定性动作）；
  5. 设备类目展示含“监控/摄像头”时退回 LLM，避免把具体摄像头指令误判成类目展示。
- **效果**：确定性场景指令省一次 MCP 往返 + 一次 LLM 调用；未量化。
- **位置**：`graph/scene_control_langgraph.py:74`、`:693`、`:709`；《UE场景控制接入说明》§8.1。

### OPT-P06 取消规划前场景快照预取（已实施）

- **问题**：以前每轮场景指令都先调一次 `get_scene_state`，把快照塞进 LLM prompt 当规划上下文；但快照只有“查状态”需要，切楼层、重置视角、设置环境等指令完全不用，页面未连接时还会白等客户端 25s 超时（并可能重试）。
- **做法**：删除 `fetch_scene_state` 节点，`init` 直连 `plan_action`；`get_scene_state` 降为普通工具，只有规则/LLM 识别出“查状态”时才在 `call_tool` 里执行一次。LLM 遇到“这层/这个设备”等指代且原话里没有参数时，直接 `need_clarify` 追问，不再靠快照猜。
- **效果**：非查状态指令不再有快照往返；查状态指令从旧逻辑的“预取一次 + 工具再调一次”变为只调一次。
- **位置**：`graph/scene_control_langgraph.py:709`、`:909`；《UE场景控制接入说明》§8.2。

### OPT-P07 场景 MCP 会话、工具与目录缓存（已实施）

- **问题**：场景指令每轮都可能参与分流；如果每次都重新握手、重新 `tools/list`、重新读 YAML，会引入不必要的网络与文件 IO；多协程同时重建会话还可能互相踢掉连接。
- **做法**：
  - `SceneMcpClient` 复用 `Mcp-Session-Id`，`list_tools()` 结果缓存在 `_tools`；
  - `_ensure_connected()` 用双检锁，保证多协程里只有一个负责重建会话；
  - HTTP 400/404（会话被 sidecar 回收）才重握手并重试一次；
  - 图内 `_load_catalog()` 缓存 catalog 文本与 `tool_map`；
  - `app.py::_scene_mcp_url()` 把 `SCENE_MCP_URL`/YAML 解析结果缓存到 `_scene_url_cache`，未配置时缓存空串并关闭场景自动识别。
- **效果**：省掉重复握手、工具列举和文件读取；避免并发互踢；未量化。
- **位置**：`mcp_client/scene_mcp_client.py:72`、`:189`；`graph/scene_control_langgraph.py:682`；`app.py:1708-1729`。

### OPT-P08 单次 encode 复用（已实施）

- **问题**：业务意图、场景分、业务查询中心分如果各算一次，同一句话要重复做 embedding 推理。
- **做法**：`classify_top_intent_with_scene()` 一次 encode 同时产出业务意图、场景分和 `business_query_score`；主流程把已经算出的 `intent` 作为 `precomputed_top_intent` 传给后续分支，不再二次 `classify_intent`。
- **效果**：每轮少一次 embedding 推理；未量化。
- **位置**：`agent/intent/classifier.py:3827`、`app.py:2044`、`:2087-2090`。

### OPT-P09 jionlp 词典 import 期预热（已实施）

- **问题**：jionlp 首次解析时间词会加载词典，第一个时间查询会额外变慢。
- **做法**：`slots.py` 模块 import 时执行 `_warmup_jionlp()`，试解析一次“今天”；失败静默，不影响主流程。
- **效果**：首次时间解析不再承担词典加载；未量化。
- **位置**：`agent/intent/slots.py:11`；《架构文档》§5.3。

### OPT-P10 关闭/降低 LLM 思考模式（已实施）

- **问题**：DeepSeek 类推理模型的思考过程会增加 token 消耗和首字延迟，而业务回答主要是“把结构化数据讲成人话”，不需要长推理。
- **做法**：`models/llm.py` 的模型配置默认 `reasoning_effort="low"` 且 `thinking="disabled"`；代码里明确说明“只传 `reasoning_effort` 不等于关闭思考”，真正关闭要传 `extra_body.thinking.type="disabled"`；两项均可被环境变量覆盖。
- **效果**：减少推理 token、降低回答延迟；未量化。
- **位置**：`models/llm.py:14-43`、`:60-87`。

### OPT-P11 兜底流水线三通道流式 + `<think>` 过滤（已实施）

- **问题**：通用兜底对话既要展示工具执行进度，又要推 LLM 原生 token 和结构化事件；推理模型的思考内容不应直接暴露给用户。
- **做法**：`graph.astream(..., stream_mode=["updates","messages","custom"])`——`messages` 转 `{event:"token"}`，`custom` 转结构化事件，`updates` 仅 debug 下发；Composer 逐 token `writer`，`<think>...</think>` 段过滤，思考结束后的正文才以 `type=answer` 外发。
- **效果**：体验优化；未量化。
- **位置**：`graph/reactive_pipeline.py:352`、`:548`；《架构文档》§9。

### OPT-P12 报告生成逐章增量写入 + 章节缓存 + 重试（已实施）

- **问题**：整份报告最后一次性生成容易超时；单章失败会导致整份重来。
- **做法**：六个章节节点顺序生成，每章完成即 `update_word` 增量写入 Word；章节内容存 `state["chapter_contents"]`；单章最多重试 2 次（`max_retries_per_chapter=2`）；`stream_output` 推章节级进度。
- **效果**：避免最后一次性生成超时，降低重复生成；未量化。
- **位置**：`graph/gen_doc_pipeline.py:95`、`:124`、`:152`；《架构文档》§10。

### OPT-P13 前端发送队列 + 单轮锁（已实施）

- **问题**：WebSocket 尚未连接时发消息会丢；一轮未结束时连续发送会造成事件交错。
- **做法**：`sendQueue` 在连接未建立时先排队、`onopen` 补发；`turnActive` 单轮锁在轮次未结束前禁用发送；断线且本轮未结束时强制 `finishTurn()` 解锁。
- **效果**：体验/稳定性优化；未量化。
- **位置**：`web/js/app.js`；《架构文档》§14。

### OPT-P14 能耗日期纯计算短路（已实施）

- **问题**：能源后端只有“今天/今年”两个有效口径；其他日期照常调用 MCP，拿回来的其实是今天数据，属于静默失真，还浪费一次后端调用。
- **做法**：`_is_supported_energy_date()` 先做纯计算判定：原话含“今天/今日/当天”或“今年/本年/年度/全年”直接放行；日期计算允许“今天 00:00 → 今天/次日 00:00”的左闭右开写法；`route_date_type` 对不支持的时间直接走 `unsupported_date` 兜底回答，不调 MCP；`realtime_electricity/realtime_water`（周对比）豁免。
- **效果**：减少无效 MCP 调用，避免“查昨天返回今天数据”的静默错误；“今天园区能耗情况怎么样？”正常出数。
- **位置**：`graph/energy_status_langgraph.py:296`、`:337`、`:363`。

## 三、稳定性与健壮性优化

### OPT-S01 MCP 逐 server 并发隔离加载（已实施，由缺陷修复演化）

- **问题**：早期把所有 server 塞进一个 `MultiServerMCPClient.get_tools()`，内部 TaskGroup 里任何一个 server 连不上（例如消防端点 404），整组调用就失败，所有域都拿不到工具，统一报“xxx 工具未加载”。
- **做法**：`get_mcp_tools()` 改为对配置里每个 server 独立 `_load_server_tools()`，用 `asyncio.gather(..., return_exceptions=True)` 并发；失败的 server 只打 `WARNING: MCP server [xxx] 工具加载失败，跳过该服务`，成功的结果照常汇总。
- **效果**：单个后端离线不再影响其他域；日志可按 server 看到加载数量。当前配置 15 个 server（含 local/knowledge/scene），`direct_client` 条目会被排除。
- **位置**：`mcp_client/mcp_loader.py:31-68`；《问题排查记录》案例 1、《缺陷跟踪表》BUG-202609-001。

### OPT-S02 单 server 定向加载 + 独立超时（已实施）

- **问题**：`get_mcp_tools()` 是“全部加载完再统一等”，业务端点不可达时 TCP 连接挂起，整组 15s 超时被取消，设备查询拿到空工具；失败日志还看不出是哪个 URL。
- **做法**：新增 `get_mcp_tools_for_server(yaml_path, server_name, timeout=15.0)`：只连一个 server、单独超时；配置缺失、`direct_client` 条目、失败、超时都返回 `[]`；错误日志带 URL 和超时秒数。`load_device_query_tools()` 只加载 `devicequery`。工具过滤为空时同时打印“期望工具名 / 实际返回工具名”。
- **效果**：设备查询从“被其他端点拖到 15s 整组超时”变为 0.5s 返回 `listDeviceOnly` + `getDeviceDetail`。
- **位置**：`mcp_client/mcp_loader.py:72`、`graph/device_query_langgraph.py:694`；《问题排查记录》案例 19。

### OPT-S03 空工具图不入缓存 + 下次查询自动重试（已实施，由缺陷修复演化）

- **问题**：各域统一 `if _xxx_graph is None: tools = await load_xxx_tools(); _xxx_graph = build_xxx_graph(tools)`。首次查询撞上后端临时不可用 → `tools={}` → 空图正常编译并永久缓存，该域“死锁”到进程重启。
- **做法**：`get_*_graph()` 在工具为空时打 `warning("... MCP 工具为空，本次不编译图，待下次查询重试")` 并 `return None`，不写模块级缓存；`run_*_graph()` 检测到 `graph is None` 时发 `error` 事件“MCP 工具暂时不可用，请稍后再试”，并按完成态处理会话状态。空判断同时覆盖“加载失败返回 `{}`”和“工具名全不匹配被过滤光”。
- **效果**：sidecar 恢复后不重启 Python，再问同一域即可正常出数。
- **位置**：`app.py:188` 等 13 处；《问题排查记录》案例 9、《缺陷跟踪表》BUG-202609-017。

### OPT-S04 LLM 格式化失败降级为原始数据（已实施）

- **问题**：LLM 没配置、调用异常或返回空时，不能让整条业务链路失败、丢数据。
- **做法**：各域 `_llm_format_*_result` 的异常全部捕获并 warning，最终 `return raw_text`；流式版本若已生成部分内容则返回已生成部分，一个 token 都没拿到才向上抛，由这里降级。
- **效果**：回答质量降级但不失败。
- **位置**：13 个业务图，如 `graph/security_status_langgraph.py:138`；`graph/stream_utils.py:60-77`；《架构文档》§7.3、§7.6。

### OPT-S05 流式回答收尾去重（已实施）

- **问题**：custom 通道已经逐 token 推过回答，收尾再转发完整 answer 会让前端显示两遍。
- **做法**：`_stream_graph_to_ws()` 返回 `(final_state, streamed_answer)`；`streamed_answer=True` 时，遍历 `final_state["events"]` 跳过 `type == "answer"` 的完整事件，只发 ask/done/error 等。
- **效果**：避免重复显示；未量化。
- **位置**：`app.py:154-180`、`:239` 等 13 处；《架构文档》§7.6。

### OPT-S06 会话状态 300 秒自动过期（已实施）

- **问题**：用户问一半走开，回来不应继续卡在旧追问里；内存字典也不能无限增长。
- **做法**：`SessionStateManager(timeout=300.0)`，`get()` 时超过 300 秒未更新自动清掉并返回 `None`；key 为 `user_id:session_id`。
- **效果**：5 分钟无更新自动清理；测试 C8 覆盖。
- **位置**：`memory/session_state.py:43-71`；《架构文档》§6、《测试方案》C8。

### OPT-S07 追问次数 / 答非所问次数双上限（已实施）

- **问题**：用户反复给半截参数或答非所问时，不能无限追问烧 token。
- **做法**：图内 `ask_count >= 3` 直接 `give_up`；handler 内 `unrelated_count >= MAX_UNRELATED(3)` 直接 `give_up`。
- **效果**：连续 3 次不相关即礼貌放弃；测试 C3/C13 覆盖。
- **位置**：`graph/*_langgraph.py` 的 `route_*`、`agent/intent/handlers/*.py:10`；《架构文档》§5.4。

### OPT-S08 场景工具失败不重试（已实施）

- **问题**：场景动作类工具如果自动重试，可能导致同一个动作重复下发（例如重复切楼层、重复撤防）。
- **做法**：`SceneMcpClient` 对工具级失败（`isError=true` / JSON-RPC error）直接抛 `SceneToolError`，不进入会话重连重试；只有 HTTP 400/404 这类会话失效才重握手后重试一次。
- **效果**：避免动作重复执行；未量化。
- **位置**：`mcp_client/scene_mcp_client.py:151-161`；《UE场景控制接入说明》§5。

### OPT-S09 `X-Session-Id` 强制后端注入 + 内部提示清理（已实施）

- **问题**：动作帧推错页面、LLM 编造会话 id、sidecar 内部提示泄露给用户。

- **效果**：安全/体验优化；未量化。
- **位置**：`graph/scene_control_langgraph.py:237`、`mcp_client/scene_mcp_client.py:14-23`、`app.py::_extract_scene_session_id`；《UE场景控制接入说明》§2、§5、§7。

### OPT-S10 ASR 超时、会话清理与纠错降级（已实施）

- **问题**：语音连接可能长时间无响应；ASR 错别字需要纠成园区域词汇；纠错失败不能丢原文。

### OPT-S13 记忆窗口 k=10 + 持久化抽象（已实施）

## 四、准确率优化

### OPT-A01 BGE 中心向量做意图分类（已实施）

- **问题**：需要毫秒级、离线、低 token 成本的意图判断，不能每条请求都调大模型。
- **做法**：`BAAI/bge-small-zh-v1.5` 编码例句，按子类型组取平均、归一化得到子类型中心，再按域取平均得到 13 个域中心；请求时 query 编码一次，与 13 个中心做点积（已 L2 归一化，等价余弦），最高分且 ≥0.65 才命中，否则 `other`；子类型分类不设阈值。
- **效果**：文档称“90% 的请求不消耗 LLM token”；意图评测从 66/88 提升到 75/88（详见 OPT-Q01/OPT-A07）。
- **位置**：`agent/intent/classifier.py:31-43`、`:3380-3386`、`:3617`；《架构文档》§5.2。

### OPT-A02 正则优先、向量兜底的分层判断（已实施）

- **问题**：纯向量分不清操作话术、业务/场景边界和槽位结构；纯正则覆盖不了新说法。
- **做法**：五层分工——①操作类话术正则拦截；②业务 vs 场景分流“正则优先、向量兜底”；③一级意图纯向量（13 域，≥0.65）；④二级意图纯向量（无阈值）；⑤slot 用正则/词典/jionlp。
- **效果**：机制分层，未量化。
- **位置**：`agent/intent/classifier.py:140`、`:168`、`:244`；`agent/intent/slots.py`；《架构文档》§5.1。

### OPT-A03 业务查询中心采用“两级平均”（已实施）

- **问题**：语料量不均衡；若把 2298 条业务例句直接平铺平均，canteen（338 条）等大域会把“业务方向”拽向自身语义。
- **做法**：先按 13 个域各聚一个中心，再让 13 个中心等权平均、归一化得到 `business_query_center`，只用于“业务 vs 场景”二选一，不参与域识别。
- **效果**：canteen 权重由平铺 14.7% 降到 7.7%，security 由 11.5% 降到 7.7%，compositive_overview 由 2.7% 升到 7.7%，每个业务主题各占 1/13。
- **位置**：`agent/intent/classifier.py:3605-3617`；《UE场景控制接入说明》§3.1。

### OPT-A04 场景分流阈值 + margin 双条件（已实施）

- **问题**：场景中心与业务中心对任意中文短句都有约 0.45 的“底分”，直接比大小会误分流。
- **做法**：强条件 `scene_score >= 0.60 且 >= business + 0.05`；弱条件 `scene_score >= 0.55 且 >= business + 0.08`；业务域命中时参照命中域分，否则参照 `business_query_score`。
- **效果**：“切到晴天”business 0.4899 / scene 0.6390 → 场景；“一楼监控数据”0.6432 / 0.6269 → 业务；“摄像头在线率是多少”0.5941 / 0.5278 → 业务。
- **位置**：`agent/intent/classifier.py:45`、`:64`、`:71`、`:168-199`；《UE场景控制接入说明》§3.1。

### OPT-A05 数据查询词/问句否决场景通道（已实施）

- **问题**：线上“查询一楼监控数据”业务分 0.6474 差 0.0026 未过 0.65 被判 `other`，场景分 0.6309 过 0.60 被场景图截胡，错误下发“显示点位”动作。
- **做法**：新增 `_DATA_QUERY_CUES` + `is_business_query()`：带数据词（数据/统计/数量/多少/在线率/占比/排名/趋势/报表/明细/清单/列表/情况/记录/日志/台账）且无明确场景动作的问法归业务；“查看 xx 情况/统计”与问句归业务；“查看 xx 设备”“转到/切到/换成/换到”明确归场景；不依赖业务域是否过阈值。
- **效果**：240 条评测集改动前后均为 218/240（91%），零回归；“查询一楼监控数据”由 other 0.6407 被场景抢走变为 device_query 0.6895；“一楼监控数据”0.6312 → 0.6792。
- **位置**：`agent/intent/classifier.py:103-165`；《语料评测记录》记录 #6。

### OPT-A06 操作类话术正则前置拦截（已实施）

- **问题**：embedding 中心向量分不清“查询口径”和“操作口径”，会议室预订、告警处置、设备控制等操作被吸进业务域，negative 误响应率 8.7%。
- **做法**：`classifier.py` 新增 `_ACTION_BLOCK_PATTERNS`（12 条正则）+ `is_action_query()`，在分类入口前置拦截，命中判 `other`（0.0 分）走大模型兜底；红线是不误伤“会议室预约统计”“未处理告警”“打开孪生巡检”“导出今天的告警清单”等合法查询口径。
- **效果**：negative 误响应率由 8.7%（9/103）降至 1.0%（1/103）；adversarial 仍为 83.7%（41/49），低于 90% 目标，8 条失败归入批 3。
- **位置**：`agent/intent/classifier.py:244-269`；《语料评测记录》记录 #5、#6。

### OPT-A07 语料边界手术 + 分批扩写（已实施）

- **问题**：基线 66/88，主要失败模式是低于 0.65 掉 other、同域子类型互抢、跨域误路由、`compositive_overview.basic_info` 吸走别域问法。

- **效果**：总分 66 → 68（手术）→ 70（批 1）→ 73（微创）→ 74（批 2）→ 75/88（记录 #6）；normal 56/71 → 61/71；energy 9/9、device_query 6/6、vehicle 7/7、meeting 6/6、information 6/6 全绿。
- **位置**：`agent/intent/classifier.py` 各 `*_EXAMPLES`；《语料评测记录》记录 #2~#4、#6。

### OPT-A08 子类型 embedding 兜底（已实施）

- **问题**：正则能保留领域排序能力，但覆盖不了新说法；直接用向量重判会破坏“省公司进了多少人”这类已排序正确的问法。

### OPT-A09 综合态势子类型 6→2、AI 预警并入安防（已实施）

### OPT-A10 设备类型别名词最长匹配（已实施）

### OPT-A11 设备查询全量 `listDeviceOnly` + 本地位置归一化过滤（已实施）

- **问题**：分页列表接口翻页容易拿不全，详情定位尤其怕漏页；“一楼”被抽成“1楼”，资产库 `spaceName` 却写作“1F”，按字面量过滤会把结果全部丢掉。
- **做法**：列表走 `device_query:listDeviceOnly`（不分页）；只下发 `syncSource`，位置在 Python 侧按 `spaceName` 过滤；`normalize_area_text()` 把 `1楼/一楼/1层/1F`统一成 `1f`，`A栋3楼`统一成 `a栋3f`；`_filter_rows_by_area()` 去路径分隔符后比较，数字两侧做边界校验（`1楼` 不误匹配 `11F/21F`）；过滤后一台不剩时直接回报“位置没有匹配的设备”，不再交给 LLM 按字面量二次筛选。
- **效果**：`1楼/一楼/1F` 等价；`A栋3楼` 能匹配 `园区/A栋/3F`；避免分页漏页。代价：设备多时返回体较大，因此尽量带 `syncSource` 筛选。
- **位置**：`graph/device_query_langgraph.py:114`、`:140`、`:231`；`agent/intent/slots.py:1432`；《问题排查记录》案例 22。

### OPT-A12 设备态势兜底反问“哪类设备”（已实施）

- **位置**：`agent/intent/handlers/device_status_handler.py`、`graph/device_status_langgraph.py`；《开发计划》§2.6。

### OPT-A13 能源“实时/现在”口径纠偏（已实施）

- **问题**：realtime 工具实际是“周对比”，语料却收录“实时用电/现在用电”，造成语义错位；`overall` 与 `realtime` 的“今日/今天”条目互相抢。

- **效果**：“今天用水多少”由 water_rank 抢走变为 overall 0.7180；“本周用水趋势怎么样”0.6499（other）→ 0.6645 翻正（仍属脆弱项）。
- **位置**：`agent/intent/classifier.py` 的 `ENERGY_STATUS_EXAMPLES`、`graph/energy_status_langgraph.py`；《语料评测记录》记录 #2、#3。

### OPT-A14 LLM 回答注入真实查询时间锚（已实施）

- **问题**：“今天食堂的菜谱是什么？”→“昨天呢”，实际查的是昨天，回答却说“今天没有查到”。原因是 prompt 只有“用户原话”和“今天日期”，slots 里真实查询时间从未进过 prompt；`original_query` 又固定传首轮原话。
- **做法**：`slots.py` 新增 `format_query_time(date_slots)`，渲染“昨天（2026-09-17 周四）”“近三天（2026-09-16 ~ 2026-09-18）”等；13 个 graph 的 `_llm_format_*` 在“用户原话”之前插入“本次查询的时间范围：{...}（回答中的时间表述以此为准，不要沿用原话里的时间词）”；person/vehicle 的 `confirm_today` 同意分支把 `date` 改写为今天。
- **效果**：省略式追问、追问补参、确认改查三条路径的回答时间与真实查询一致；未量化。
- **位置**：`agent/intent/slots.py:282`、各业务图；《问题排查记录》案例 11。

### OPT-A15 时间澄清支持“今天/昨天/前天”（已实施）

- **问题**：bot 追问“近几天”，用户答“今天”，被回“没太理解，请说具体天数”。澄清分支只认 `近N天`、`三天/一周/月`、序数选择，不认点日；主流程 `parse_time_slot` 却认，形成两套口径。
- **做法**：`slots.py` 新增 `parse_point_day(query)`，解析“今天/今日/当天”“昨天/昨日”“前天”，生成与 `parse_time_slot` 手工段同构的 `{span, start, end, raw}`；10 个 handler 的 `_pending_date_clarify` 分支在拒绝判定之后、区间解析之前接入，命中则回写 `slots.date`、清标记、`action=continue` 重跑图。
- **效果**：“最近发布了哪些信息？”→“今天”直接查今天并出数；无关内容仍走原 re_ask/give_up。

### OPT-A16 能源日期按语义判定 + 双保险（已实施）

- **问题**：能源后台只有“今天/今年”两个口径，图内原先没有日期校验，“昨天”也会照常调无参 GET，返回的其实是今天数据；后续又按解析形状硬卡 `start.date()==end.date()==today`，jionlp 对“今天园区能耗情况怎么样？”解析出 `[今天00:00, 次日00:00)`，导致合法的“今天”被误杀。
- **做法**：`_is_supported_energy_date()` 改为语义判定 + 双保险：原话 `raw` 含“今天/今日/当天”或“今年/本年/年度/全年”直接放行；日期计算兜底允许起点在今天、终点在今天或次日零点；今年允许起点 1 月 1 日、终点不越过次年 1 月 1 日；`fromisoformat` 前统一 `str()`，None/异常格式返回 False；周对比子类型豁免。
- **效果**：“今天”正常出数；“昨天呢”“上周的能耗”“近三天的用水量”走兜底回答；“今年能耗”“年度用电”放行。

### OPT-A17 子类型继承兜底值保护 + 人员离开正则（已实施）

### OPT-A18 省略式追问：拼接串只喂分类器，槽位只用本轮输入（已实施）

### OPT-A19 追问轮 `extract_slots(is_followup)` 只抽填空字段（已实施）

### OPT-A22 场景 `env_time` 归一化为 `HH:MM:SS`（已实施）

- **问题**：服务端下发 `env_time:"中午"/"白天"`，sidecar 实际要求 24 小时制时间字符串（如 `"12:00:00"`）；用户说“下午一点”也不会换算成 `13:00:00`。
- **做法**：`scene_control_langgraph.py` 新增中文时刻解析链路：`_parse_scene_time()` 支持 `HH:MM(:SS)`、`N点/M分`、`半/一刻/三刻`、中文数字、全角数字与冒号；`_apply_period()` 按“凌晨/早上/上午/中午/下午/傍晚/晚上/夜晚/深夜”换算 24 小时制；`_format_clock()` 统一输出 `HH:MM:SS`；`_normalize_env_args()` 改为“用户原话优先于 LLM 返回值”，两者都解析不出时丢弃 `env_time` 并追问；LLM 规划 prompt 明确要求 `HH:MM:SS`。
- **效果**：`改成下午一点`→`13:00:00`、`早上9点`→`09:00:00`、`下午一点半`→`13:30:00`、`晚上7点15分`→`19:15:00`、`晚上十二点`→`00:00:00`、`下午三点一刻`→`15:15:00`；`25点`不解析走追问；纯天气指令不附带 `env_time`。
- **位置**：`graph/scene_control_langgraph.py:411`、`:469`；《缺陷跟踪表》§9 BUG-202611-008。

### OPT-A23 序数指代解析（已实施）

- **问题**：消防反问“设备台账、告警统计、实时告警、月度报修”，用户答“就第一个吧”，机器人判为不相关并复读。选项列表问完就扔，`extract_slots` 只对当前句做正则/embedding，解析不了序数；短回复规则 `len≤4` 也救不了（“就第一个吧”5 个字）。

- **效果**：“就第一个吧”能正确解析为设备台账，不再复读。
- **位置**：`agent/intent/slots.py:99`；《问题排查记录》案例 6。

### OPT-A24 消防笼统问法改为反问（已实施）

- **问题**：“查下最新的消防”正则抽不到子类型落 `count` 兜底；消防 `_JAVA_TOOL_MAP` 只有 `fire_assets/fire_alarm_num/fire_alarm_list/month_repair`，没有 `count`，于是必然进守卫分支返回“该查询类型当前 MCP 后端暂不支持”。

- **效果**：笼统问法不再必然失败，用户可从选项中选择。
- **位置**：`graph/emergency_fire_langgraph.py`、`agent/intent/handlers/emergency_fire_handler.py`；《问题排查记录》案例 2。

### OPT-A25 时间解析优先级链 + 模糊/未来时间处理（已实施）

- **问题**：中文时间表达多样，解析顺序错误会导致“上周”被当“近一周”、模糊时间直接查错范围。

- **效果**：行为正确性优化；`tests/test_slots.py` 覆盖。
- **位置**：`agent/intent/slots.py:126-240`；《架构文档》§5.3。

## 五、多轮对话与体验优化

### OPT-E01 完成态保留 300 秒 + 拼接重分类（已实施）

- **问题**：查询完成后各 `run_xxx_graph` 尾部 `session_state.clear()`，上下文归零；第二轮“昨天呢”与任何域中心向量相似度都低于 0.65 → `other` → 走兜底。
- **做法**：10 个域查询结束（无 ask 事件）不再 clear，改为 `state.done=True`、`missing_params` 清空后继续保留，靠 `SessionStateManager` 的 300 秒超时自动过期；用 `is_waiting`（有状态且 `not done`）区分“追问态/已完成态”；新增情况 1.5：`top_intent == "other"` 且存在 done 状态时，用上一轮 `original_query` 拼接本轮输入重新 `classify_intent`，命中业务域则按继承式启动。
- **效果**：5 分钟窗口内“昨天呢”“那前天呢”可续查；未量化延迟影响。
- **位置**：`app.py:267`、`:2249-2289`；《问题排查记录》案例 8。

### OPT-E02 追问态新意图接管（已实施）

- **问题**：追问态下用户直接说新需求，被复读问题吞掉。因为活跃会话时完全跳过意图分类，固定进当前模块 handler；`is_related()` 退化为纯关键词匹配，识别不了“这是别的域的新需求”。用户重复新需求，第 3 次触发 give_up，第 4 次才能正常路由。
- **做法**：`is_related=False` 时先跑一次 `classify_intent`：识别出其他域意图且过阈值 → 放弃当前任务、清状态、按新意图走全新流程；仍是本域/other → 维持 re_ask。只有疑似跑题时才付费编码。
- **效果**：追问中可直接换意图；测试 C4 覆盖。
- **位置**：`app.py:2149-2179`；《架构文档》§4.4、《测试方案》C4。

### OPT-E03 取消分支补发 `done` 事件（已实施）

- **问题**：追问态回复“不用了”，后端 `give_up` 分支只发 `{"type":"answer"}` 就 `continue`，没有发 `{"type":"done"}`；前端 `turnActive` 只在 `finishTurn()` 复位，而 `finishTurn` 仅由 `done`/`ask`/`error` 触发，结果是转圈永不消失、输入框永久锁死。
- **做法**：`app.py` give_up 分支在 answer 之后补发 done，对齐 graph 约定；核对全部裸发事件点，确认只有 give_up 漏发。
- **效果**：取消后转圈立即消失、输入框恢复可用。
- **位置**：`app.py:2130-2148`；《问题排查记录》案例 14。

### OPT-E04 收尾语整句拦截（已实施）

- **问题**：取消后用户答“没有了”，`active_state=None` → 全新分类判 `other` → 兜底回“对不起，我目前掌握的能力无法解决你的问题”。这句话的真实语义是对“还有其他问题吗”的礼貌收尾，不该被当成待分类的新查询。
- **做法**：`app.py` 新增 `_CONVERSATION_CLOSE_RE` + `is_conversation_close()`，在意图分发前拦截（情况 1.4，排在情况 1.5 之前）：整句匹配，允许“我说”“就是”等口头铺垫、“没有了谢谢”这类后置致谢、吧/啦/呀等语气尾；核心词包括“没有了/没了/没有/不用了/暂时没有/再见/拜拜/谢谢/辛苦了/好的”；长度上限 12 字 + 收尾字符类闭合，保证“没有告警吗”“没有什么新闻”这类真查询不被误吞；只拦 `top_intent == "other"`。
- **效果**：礼貌收尾；完成一轮查询后单独发“没有了”不再重新执行上轮查询；真查询不误吞。
- **位置**：`app.py:1542-1565`、`:2237`；《问题排查记录》案例 15。

### OPT-E05 省略式追问路由优先级收紧（已实施）

- **问题**：拼接分支原先只在 `top_intent == "other"` 时触发；“昨天呢”这类短承接语若碰巧过某域 0.65 阈值，会优先走全新流程，然后因缺人名反问“请问查谁？”。
- **做法**：在 `top_intent` 计算后、if/elif 分支前加预处理：仅当上一轮已完成且输入是省略式追问形状（`is_ellipsis_followup` 白名单：时间词/域动词+语气词）时，用“上轮原话 + 本轮输入”重新分类；命中业务域则按继承式启动。非省略形状的 `other`（“今天日期”“你好”）不再拼接。
- **效果**：对老 query 零影响，只收紧短承接语路径。
- **位置**：`app.py:1589`、`:2250-2299`；《对话逻辑修改方案》§2.3。

### OPT-E06 追问态跳过意图分类（已实施）

- **问题**：已有进行中的追问任务时再跑意图分类既浪费模型调用，又可能把“近三天”这类补参误分类。
- **做法**：`is_waiting` 时直接走 `handler.handle_reply`，不跑 `classify_intent`；非追问态才计算一次并在后续分支复用 `precomputed_top_intent`。
- **效果**：每轮追问省一次意图分类调用；避免补参被误分类。
- **位置**：`app.py:2004-2092`；《架构文档》§4.4。

### OPT-E07 LLM 空数据/追问禁令（已实施）

- **问题**：安防查询空数据后，LLM 在“口语化”要求下自由发挥“要不要我帮你查一下其他时间段？”；用户答“可以”时已无活跃状态，`classify_intent("可以")` 判 `other`，掉兜底。这句话随 `answer` 发出，不是 `ask` 事件，`keep_state` 不保留状态，会话被清空。
- **做法**：各业务域 `_llm_format_*_result` prompt 统一加两条禁令：空数据只如实说明、不得建议查其他时间段；禁止任何追问/提议/反问。
- **效果**：消灭“LLM 承诺系统没有的路径”的协议脱节；方案 B（空结果显式 ask）仍列为长期项。
- **位置**：13 个业务图；《问题排查记录》案例 7、《缺陷跟踪表》BUG-202609-007。

### OPT-R05 预热开关与场景地址覆盖（已实施）

- **问题**：不同部署环境可能需要关闭预热或覆盖 sidecar 地址。
- **做法**：`PREWARM_ON_STARTUP=0/false/off/no` 关闭预热；场景地址可用 `SCENE_MCP_URL` 覆盖（优先级高于 YAML）；场景客户端默认超时 25s，要求大于 sidecar 的 `scene.action-timeout-ms` 15s。
- **效果**：部署灵活性提升；未量化。
- **位置**：`app.py:1772`、`mcp_client/scene_mcp_client.py:24-34`；《UE场景控制接入说明》§7、§8.3。

## 七、工程效率与质量保障

### OPT-Q01 意图评测分级门禁 + negative/adversarial 集（已实施）

- **问题**：原先没有负样本和对抗集，normal 越准，操作类误响应越隐蔽。
- **做法**：`tools/eval_intent.py` 新增 `negative`（103 条域外负样本，期望 other）与 `adversarial`（49 条加噪变体，期望原意图）；退出码分级：normal/boundary/incident 逐条硬门禁，negative 误响应率 ≤5%、adversarial 通过率 ≥90%，环境变量可覆盖；输出新增“误判流向”。
- **效果**：negative 8.7% → 1.0%；adversarial 83.7%（41/49），仍低于 90% 目标；240 条评测集 218/240（91%）。
- **位置**：`tools/eval_intent.py`；《测试方案》§2、§10，《语料评测记录》记录 #5、#6。

### OPT-Q02 语料生成器改造与人工审查纪律（已实施）

- **问题**：早期生成器产出泛化问法、时间口径漂移、跨域吸引、重复条目，直接回写会污染中心向量。
- **做法**：`generate_intent_examples.py` 增加“陈述式请求”第 5 种风格、疑问句硬约束放开、核心词锚定、时间口径保护；`SUB_TYPE_TARGET_COUNT` 25→35，且 `target=max(上限, 已有条数)`、人工条目排前；生成后逐条红线审查（删 51 改 2）；对比/曲线类子类型禁用生成器，只手写；问号/“今日 vs 今天”不参与去重，审查必盯组内近似三连。
- **效果**：批 1 语料 451 → 约 790 条；避免生成条目把已有大组挤掉；具体翻绿见 OPT-A07。
- **位置**：`agent/intent/generate_intent_examples.py`；《语料评测记录》记录 #3。

### OPT-Q03 多轮上下文场景矩阵（部分实施）

- **问题**：追问、放弃、接管、子类型继承、超时、跨会话隔离等缺少系统回归集。
- **做法**：按“多轮对话 + 每轮断言”设计 13 个场景；C1/C4/C5/C6 已落地为 `tests/test_context_scenarios.py`（模块级 case 元组 + `@pytest.mark.parametrize`，不 import `app.py`，接管判定与省略式槽位合并以“规格快照”复刻）；C7~C13 仍待补充。
- **效果**：C1/C4/C5/C6 已覆盖；未量化。
- **位置**：`tests/test_context_scenarios.py`；《测试方案》§4。

### OPT-Q04 性能基准测试（已实施）

- **问题**：需要基线化分类、槽位、图执行、并发、loader 隔离等关键路径耗时，防止性能回退。
- **做法**：`tests/test_performance.py` 覆盖正则槽位抽取（8 域）、顶层意图分类、消防子类型分类、单图端到端、30 路图并发、`handle_reply` 延迟、MCP loader 单点隔离；阈值可用 `PERF_*` 环境变量覆盖。
- **效果**：7 项基准可执行；阈值示例：分类 P95 < 3000ms、单图 P95 < 300ms（可用环境变量调整）。
- **位置**：`tests/test_performance.py`；《测试方案》§8。

### OPT-Q05 测试桩化重依赖（已实施）

- **问题**：本机依赖不全、无 GPU、无 Java 后端，真实链路跑不起来。
- **做法**：`tests/conftest.py` 用 FakeTool/FakeLLM 等桩替代 MCP 与模型，直接导入项目真实模块验证图逻辑；真实运行环境为 Linux 容器。
- **效果**：本机无 GPU/无 Java 后端也能跑 pytest；未量化。
- **位置**：`tests/conftest.py`；《架构文档》§15。

### OPT-Q06 追问话术一致性测试（已实施）

- **问题**：handler 的 `generate_question` 与 graph 的 `ask_param` 文案不一致，会导致同一缺失参数出现两套追问话术。
- **做法**：`tests/test_handlers.py::TestQuestionConsistency` 校验各域 handler 与 graph `ask_param` 输出逐字一致。
- **效果**：防回归；未量化。
- **位置**：`tests/test_handlers.py:186`；《开发计划》§2.5。
