## 0. 结论摘要

一次「楼层切换 + 多步指令 + 列表指代 + 业务追问」的联调对话暴露出六类问题，均已在代码中定位：

| 编号 | 用例 | 结果 | 严重度 |
|---|---|---|---|
| UE-FAIL-001 | 用户说「切2楼」，助手回「2F 匹配到 60 台设备，请补充设备类型」 | 失败：楼层指令被设备解析拦截 | S2 |
| UE-FAIL-002 | 用户说「按楼层一层一层从下往上切楼」，助手下发 `scene_switch_floor(floor=2)` | 失败：追问态吞掉新指令 + 旧楼层污染参数 + 多步指令被静默降级 | S1 |
| UE-FAIL-003 | 用户可见「已下发动作 scene_switch_floor (floor=2, focus=true)」 | 失败：内部工具名和原始参数直接暴露给用户 | S3 |
| UE-FAIL-004 | 「切回主楼」下发 `scene_reset_view`，「展示整栋楼」下发 `scene_switch_floor(floor=99)` | 失败：同一语义被映射成两个不同动作，前者只复位相机、不恢复整栋楼 | S2 |
| UE-FAIL-005 | 「展示1楼设备」后说「打开其中一个」，助手返回跨楼层的 12 台设备 | 失败：列表上下文丢失 + 选择类指代不识别 + 无过滤时查全表 | S1 |
| UE-FAIL-006 | 业务追问「查哪一层」后回答「三楼」，却被下发 `scene_switch_floor(3)`；「4楼」被告知没有告警，但接口不支持楼层过滤 | 失败：业务追问是自由文本、裸楼层被场景抢走、当前楼层/楼层告警能力边界缺失 | S1 |

六个问题的共同点：**场景通道只覆盖了“理想路径”**——默认用户每句话都在补上一轮参数、默认指令都是单步动作、默认 sidecar 文案可以直接给用户看。

## 1. UE-FAIL-001：楼层指令被设备解析拦截

### 1.1 对话复现

```
用户：切2楼
助手：2F 楼层匹配到 60 台设备（先列出前 12 台）。
      请补充设备类型（监控/门禁/广播等），或直接说点位名称/序号：
```

同一用户说「切到2楼」则能正常切层。两句话语义几乎一致，行为完全不同。

### 1.2 期望

进入场景图，调用 `scene_switch_floor`，下发 `floor=2`。

### 1.3 根因

场景图之前有一层「设备名 → 点位 tag」预解析（[app.py:1990-1996](../app.py#L1990-L1996)），触发条件是 [scene_resolve.has_device_reference()](../agent/loop/scene_resolve.py#L94-L114)。该函数用**手写动作词表 + 残留长度阈值**判断“这句话是不是在说某台设备”：

```python
residual = _STRIP_ACTION.sub("", text).strip(" 的，,。：:")
if len(residual) < 3 or _SCOPE_WORD.search(residual):
    return False
return True
```

而动作词表 [scene_resolve.py:81-84](../agent/loop/scene_resolve.py#L81-L84) 只有：

```
切回|切到|切换到|切换|回到|返回|退出|关闭|...
```

**没有裸的「切」。**

| 话术 | 剥动作词后 | 长度 | `has_device_reference` | 实际走向 |
|---|---|---|---|---|
| 切到2楼 | `2楼` | 2 | False | 场景图，切到 2F ✅ |
| 切换2楼 | `2楼` | 2 | False | 场景图 ✅ |
| **切2楼** | **`切2楼`** | **3** | **True** | **设备台账，返回 2F 全部 60 台 ❌** |
| 去2楼 | `去2楼` | 3 | True | 设备台账 ❌ |
| 转2楼 | `转2楼` | 3 | True | 设备台账 ❌ |

被判成设备线索后，[scene_resolve.resolve_scene_device_tag()](../agent/loop/scene_resolve.py#L208-L275) 调 `find_devices`：

- `normalize_floor("切2楼")` 能正确得到 `2F`（[device_query.py:683](../agent/loop/domains/device_query.py#L683)）；
- 但没有设备名称关键词，于是返回该层全部设备；
- 最终落到 [scene_resolve.py:266](../agent/loop/scene_resolve.py#L266) 的 `scope = "2F 楼层"` 和 [scene_resolve.py:274](../agent/loop/scene_resolve.py#L274) 的“请补充设备类型”话术。

### 1.4 违反的契约

- **楼层识别器和设备线索判定器口径不一致**：`normalize_floor` 认识 `2楼 / 2F / 负一层`，`_SCOPE_WORD` 却只认识“楼层 / 整层 / 全楼 / 楼栋”，没有结构化楼层。
- **用字符长度当语义判断**：`len(residual) >= 3` 是经验值，不是意图识别；`切2楼` 恰好 3 个字越线，`切到2楼` 恰好 2 个字没越线。
- **动作词枚举必然漏词**：补上「切」之后，`去2楼`、`转2楼`、`上2楼`、`跳2楼` 仍会误判。

> 备注：这里**不要用文本相似度阈值修**。代码当前没有任何相似度判断；「切2楼」和「切到2楼」相差 25% 只是暴露了枚举式判定的脆弱性，正确做法是结构化归一化，而不是调阈值。

### 1.5 修复建议

改 `has_device_reference`：先剥动作词，再把楼层/范围表达整体归一化掉，最后看**还剩什么**：

```python
def has_device_reference(query: str) -> bool:
    text = (query or "").strip()
    if not text:
        return False
    if _ORDINAL_RE.search(text) or _PRONOUN_RE.search(text):
        return True
    if _TYPE_WORD_RE.search(text):
        return True
    if _ENV_WORD.search(text):
        return False
    residual = _STRIP_ACTION.sub("", text)
    residual = _FLOOR_PHRASE.sub("", residual)   # 新增：2楼/2F/一层/负一层/B1
    residual = re.sub(r"[\s的，,。：:楼层整全所有]", "", residual)
    return bool(residual)
```

回归要求：

- `切2楼` / `切到2楼` / `去2楼` / `转2楼` → 不查台账，进场景图；
- `打开2楼通道东向西` → 仍查台账（楼层被剥掉后还剩“通道东向西”）；
- `2楼的监控` → 仍查台账（类型词先命中）；
- `第三个` / `这个` → 仍按候选解析。

## 2. UE-FAIL-002：追问态吞掉新指令，旧楼层污染参数

### 2.1 对话复现

承接 UE-FAIL-001 的追问态（系统正在等用户选设备）：

```
用户：按楼层一层一层从下往上切楼
助手：已下发动作 scene_switch_floor (floor=2, focus=true)。
```

### 2.2 期望

至少满足其中一条：

1. 识别出用户没有在回答“选哪台设备”，放弃追问态，按新指令重新规划；
2. 识别出“一层一层/从下往上”是**多步流程诉求**，而 `scene_switch_floor` 一次只能切一层，明确告知不支持并询问起始楼层；
3. 任何情况下都不能从上一轮的 `2F` 推断出本轮的 `floor=2`。

### 2.3 根因（三步叠加）

**第一步：追问态无“新指令退出口”**

[app.py:2291-2318](../app.py#L2291-L2318) 只要上一轮场景追问没结束（`scene_waiting=True`），就把本轮话术当成补答，并拼成：

```python
merged_query = f"{scene_prev.original_query} {query}"   # app.py:2293
```

然后 [app.py:2352-2356](../app.py#L2352-L2356) 把 `merged_query` 交给场景图。代码没有判断“本轮这句话是否真的在回答上一问”。唯一的相关校验在设备解析内部的 `_answers_pick` / `ESCAPE_CLARIFY`（[scene_resolve.py:117-128](../agent/loop/scene_resolve.py#L117-L128)、[241-246](../agent/loop/scene_resolve.py#L241-L246)），但本句 `has_device_reference` 为 False，根本没进那一层。

**第二步：旧参数进入规划上下文**

拼好的 `merged_query` 里带着上一轮的 `2F`。由于 `ask_count > 0` 且有 `last_question`，场景图的规则快通道被禁用（[scene_control_langgraph.py:746-750](../graph/scene_control_langgraph.py#L746-L750)），直接交给 LLM。提示词第 4 条又规定“需要连续执行多个动作时，只选用户本次最主要的一个”（[scene_control_langgraph.py:769](../graph/scene_control_langgraph.py#L769)）。LLM 从旧上下文里抓了唯一具体的楼层 `2F`，把“一层一层从下往上”这个流程诉求静默降级成一次单层切换。

**第三步：没有能力守卫和参数接地**

- 没有任何逻辑检查“用户要的动作，工具是否支持”；
- 没有校验 `floor=2` 是否来自本轮话术；
- 如果走规则兜底，`_extract_floor("按楼层一层一层从下往上切楼")` 会从“一层一层”里抠出 `1`（[scene_control_langgraph.py:519](../graph/scene_control_langgraph.py#L519)、[642-644](../graph/scene_control_langgraph.py#L642-L644)），同样会瞎下发一层。

**补充：UE 不回执**

即使把多步指令实现成循环调用，场景侧也没有完成回执（设计注释见 [scene_control_langgraph.py:25](../graph/scene_control_langgraph.py#L25)），“一层一层切完再下一步”无法可靠编排。批量/巡游需要 sidecar 提供专门工具，见 [loop-agent-TODO.md](loop-agent-TODO.md) T19。

### 2.4 违反的契约

| 契约 | 本次表现 |
|---|---|
| 追问态只接受“对缺失参数的补充” | 用户换了新指令，仍被拼进旧追问继续执行 |
| 参数必须可归因于本轮话术 | `floor=2` 来自上一轮的 “2F” |
| 不支持的能力要明说，不能降级成相似动作 | “一层一层从下往上”被下发成一次 `floor=2` |
| 一步动作只能做一步，不能假装完成 | 回答“已下发”，但用户的流程诉求完全没有执行 |

同类问题在业务域已经修过：追问态新需求被复读吞掉（[缺陷跟踪表 BUG-202609-005](缺陷跟踪表.md)）、拼接串导致实体抽错（BUG-202609-010）、场景通道误吞数据查询（BUG-202611-001）。场景通道没有复用这些教训。

### 2.5 修复建议

1. **追问态解绑**：把“待补问题”和“本轮原话”分开传。先判断本轮是否在回答待补问题（序号/设备名/缺失参数值）；不是就清掉场景追问态，按新指令重新规划。
2. **能力守卫**：命中 `一层一层|依次|逐个|从下往上|循环|每层|自动` 等流程语义，而选中工具是单次动作时，返回固定追问，禁止下发。例如：
   > 目前一次只能切一层，您想先切到哪一层？
3. **参数接地**：楼层类指令优先用本轮原话 `_extract_floor(当前句)`；模型给出的参数若在本轮话术里找不到依据，改成追问。
4. **状态语义**：场景追问态补上“新意图/新指令接管”通道，与业务域的 `re_ask` 保持一致。

## 3. UE-FAIL-003：内部工具名与原始参数直出

### 3.1 现象

```json
{"event":"custom","data":{"type":"answer",
 "content":"已下发动作 scene_switch_floor (floor=2, focus=true)。"}}
```

### 3.2 期望

面向用户的表述只描述结果，例如：

> 已下发：切换到 2F。

工具名、参数、`focus` 这类内部字段只进日志。

### 3.3 根因

[scene_control_langgraph.py:868-895](../graph/scene_control_langgraph.py#L868-L895) 的 `call_tool` 把 sidecar 返回文本交给 `_clean_scene_text`，而后者只清“回复用户时不要说…”“UE 不回执”等内部提示（[scene_control_langgraph.py:234-252](../graph/scene_control_langgraph.py#L234-L252)），不做工具名→中文、参数→人话的转换。

该格式目前还被写进 [UE场景控制接入说明.md](UE场景控制接入说明.md) §5 的“成功下发”示例，属于**已被文档固化的现状**，不是偶发。

### 3.4 修复建议

在 `call_tool` 里增加结果格式化：

- `_TOOL_LABELS` 已有工具中文名映射（[scene_control_langgraph.py:30-51](../graph/scene_control_langgraph.py#L30-L51)）；
- 对 `scene_switch_floor` 输出“切换到 N 层”，对 `scene_set_env` 输出“环境已切换为 …”；
- 未知工具回退到中文动作名，不输出原始参数；
- 原始 `tool_result` 仍保留在 state / 日志里供排查。

## 4. UE-FAIL-004：「切回主楼」被映射成「重置视角」

### 4.1 对话复现

```
用户：切回主楼
助手：已下发动作 scene_reset_view。

用户：展示整栋楼
助手：已下发动作 scene_switch_floor (floor=99, focus=true)。
```

现象：第一句只复位了相机，楼层隔离仍在，画面停在当前楼层；第二句才真正回到整栋楼。

### 4.2 期望

两句话表达的是同一个用户意图，都应回到整栋楼：

```json
{"tool": "scene_switch_floor", "arguments": {"floor": 99, "focus": true}}
```

至少两句话必须走同一个工具，不能一个复位相机、一个改场景状态。

### 4.3 根因

**第一步：词表缺口，「主楼」不在整栋同义词里**

[scene_control_langgraph.py:515](../graph/scene_control_langgraph.py#L515) 的整栋词表只有：

```
整栋|全楼|整座|整幢|整楼|全栋|楼栋
```

没有「主楼 / 主楼栋 / 科研办公楼」。因此 `_extract_floor("切回主楼")` 返回 `None`，规则快通道出不了计划，落到 LLM。而「展示整栋楼」命中「整栋」→ `99`，快通道直接下发 `scene_switch_floor(99)`。

**第二步：提示词也没告诉模型「主楼 = 99」**

[scene_control_langgraph.py:762](../graph/scene_control_langgraph.py#L762) 只写了：

> 11/99=整栋楼（用户说“楼栋/整楼/全楼”都填 99）

没有「主楼」。模型看到「切回主楼」更像“回到主视角”，于是选了 `scene_reset_view`。

**第三步：两个工具的语义差异没有进入规划上下文**

| 工具 | 前端映射 | 影响相机 | 影响楼层/楼栋状态 | 能否退出楼层隔离 |
|---|---|---|---|---|
| `scene_reset_view` | `ResetView` | 是 | 否 | **否** |
| `scene_switch_floor(99)` | `showFloor(99)` | 是（分支自带 `ResetView`） | 是（显示楼栋、隐藏楼层） | **是** |

对应代码：

- `scene_reset_view` 只发 `ResetView`（`tf_park_ue/src/utils/uePlayer/sceneExecutor.ts:197`）；
- `scene_switch_floor(99)` 走 `useSplitBuild.ts` 的 `floorNum >= 11` 分支：`ViewActor` 楼栋 → `HideActor` 楼层 → `ResetView`（`tf_park_ue/src/hooks/useSplitBuild.ts:58-77`）。

所以「切回主楼」下发 `ResetView` 后，楼层隔离（`floorNum < 11` 分支隐藏楼栋、显示楼层）仍然生效，用户当然看不到整栋楼。

**第四步：回答只报工具名，掩盖了差异**

用户看到的是 `scene_reset_view` vs `scene_switch_floor`，两个英文工具名无法让他判断“前者没有回到主楼”，同 UE-FAIL-003。

### 4.4 违反的契约

| 契约 | 本次表现 |
|---|---|
| 同一语义 → 同一工具 | “回主楼”和“展示整栋楼”走成两个不同工具 |
| 工具选择要覆盖口语同义词 | “主楼”没进整栋词表 |
| 回答要能区分动作结果 | “重置视角”和“回到整栋楼”在用户侧看不出区别 |

已有测试 `test_restore_building_plans_switch_floor_99`（[tests/test_loop_scene_resolve.py:349](../tests/test_loop_scene_resolve.py#L349)）覆盖了「恢复楼栋 / 切回楼栋 / 切回整栋楼」，但**没有覆盖「主楼」**，所以测试全绿也没拦住这次线上问题。

### 4.5 修复建议

1. **补词表**：`_extract_floor` 增加 `主楼|主楼栋|科研办公楼` → `99`；`_SCOPE_WORD` 同步增加「主楼 / 办公楼」，避免进场景图前被设备解析当成设备名。
2. **补提示词**：把“主楼 / 主楼栋 / 科研办公楼”加入 `99` 的同义词说明。
3. **加一致性守卫**：query 含 `主楼|整栋|全楼|楼栋` 等整栋语义、但没有 `视角|视野|镜头` 等相机词时，禁止选 `scene_reset_view`；若模型仍选了，改判 `scene_switch_floor(99)` 或追问。
4. **区分回答文案**：「已切回整栋楼」/「已重置视角」分开表述，且不输出工具名。
5. **回归用例**：见 R11–R13。

## 5. UE-FAIL-005：列表之后说「打开其中一个」，上下文丢失并返回全园区设备

### 5.1 对话复现

```
用户：展示1楼得设备
助手：122 台设备（园区共 579 台），楼层 1F + 设备标签列表

用户：打开其中一个
助手：匹配到 12 台设备，请选择
      （列表里出现 1F / 2F / 3F / 4F / 6F / 9F / -1F 的设备，与上一轮 1F 无关）
```

用户感知：这一轮没有结束，而且答非所问。

### 5.2 期望

「其中一个」是对上一轮列表的指代。正确处理应该是：

1. 从上一轮的 122 台里解析指代；
2. 122 台无法唯一确定时，追问“要打开哪一台？可以点上方设备标签，或说名称/编号”；
3. 用户说「第一个」时，按上一轮列表的第一台解析；
4. 任何情况下都不要重新查全园区台账，把无关楼层的 12 台当成候选。

### 5.3 根因

**A. 列表上下文没有跨通道保存**

- 上一轮的 122 台由 loop L1 `device_query__list` 产出，首行来自 [device_query.py:535-555](../agent/loop/domains/device_query.py#L535-L555) 的 `_summary()`；
- `PipelineResult.entities` 只被 [ws_bridge.py:213-219](../agent/loop/ws_bridge.py#L213-L219) 发给前端，**没有写回任何会话状态**；
- `Session`（[pipeline.py:27-47](../agent/loop/pipeline.py#L27-L47)）只有 `history` 和 `pending`，没有“最近一次列表”；
- 本轮被场景通道接管后，`run_scene_control_graph` 的 `prev_candidates` 只从 `session_state` 的 `scene_control` 槽里取（[app.py:1981-1985](../app.py#L1981-L1985)）。上一轮不是场景追问，所以候选为空。

结果：「其中一个」在场景通道里没有任何指代对象。

**B. 选择类指代没有被识别**

- `_PRONOUN_RE` 只有 `这个|那个|这台|那台|它|该设备`（[scene_resolve.py:42](../agent/loop/scene_resolve.py#L42)），没有「其中一个 / 其中一台 / 里面一台 / 随便一台」；
- `_answers_pick` 只认序号或设备关键词（[scene_resolve.py:117-128](../agent/loop/scene_resolve.py#L117-L128)），也不认这些选择短语；
- 所以即使用户上一轮真的拿到了场景候选，「其中一个」也会落到 `ESCAPE_CLARIFY`，而不是选中。

**C. 没有过滤条件时直接查全表**

- `has_device_reference("打开其中一个")` 剥掉「打开」后剩「其中一个」（4 个字）→ 返回 `True`；
- `find_devices` 没有楼层、没有关键词 → 返回全园区 579 台；
- `rows = matched[:12]` → 取前 12 台，天然跨楼层；
- `candidate_entities` 的标题只写 `匹配到 12 台设备`，不带 `total`（[scene_resolve.py:200](../agent/loop/scene_resolve.py#L200)），用户看不到“其实是 579 台里随便截的 12 台”。

**D. 轮次在状态机层面没有结束**

- 这一轮发的是 `ask`（[app.py:2023-2028](../app.py#L2023-L2028)），动作没有执行；
- `session_state` 以 `done=False` 保留（[app.py:2029-2038](../app.py#L2029-L2038)），后续任何一句话都可能被当成补答（同 UE-FAIL-002）；
- 前端即使收到 `done` 事件解锁输入框，对话在业务语义上仍停在“等你选设备”。

### 5.4 违反的契约

| 契约 | 本次表现 |
|---|---|
| 指代必须能回溯到上一轮的实际对象 | 「其中一个」没有回溯到 122 台列表 |
| 无过滤条件不能退化成全量查询 | 返回了全园区前 12 台 |
| 追问必须给出真实候选集 | 候选与上一轮 1F 列表无关 |
| 列表标题要反映真实总量 | 卡片写 12 台，实际是 579 台里截的 12 台 |

### 5.5 修复建议

1. **保存最近一次列表**：`PipelineResult.entities` 发送后，同时按 `user:session` 存一份精简快照（id / label / code / floor / total），供下一轮指代解析；场景通道和 loop 通道共用同一个 store。
2. **补选择类指代**：`_PRONOUN_RE` 增加 `其中一个|其中一台|里面(的)?(一台|一个)|随便(一台|一个)`；`_answers_pick` 把「其中一个」视为“需要二次确认的选择”，而不是设备名。
3. **无候选时的固定话术**：选择类短语 + 没有候选/过滤条件 → 直接回“要打开哪一台？可以点上方设备标签，或说名称/编号”，**不要调用 `find_devices`**。
4. **有候选时按序号选**：「第一个 / 最后一个 / 第 N 个」从最近列表解析；「其中一个」多台时继续追问，不随机选。
5. **卡片标题带 total**：`candidate_entities` 增加 `total` 参数，标题写成“122 台中的第 1–12 台，请选择”。
6. **状态收尾**：无候选的澄清不要留 `done=False` 的追问态，或至少把“未识别到指代”作为退出条件清状态。

### 5.6 与 UE-FAIL-002 的关系

同一类“上下文只在各自通道内维护”的问题：UE-FAIL-002 是“旧追问吞掉新指令”，本条是“新指令找不到旧列表”。两者都需要一个统一的“最近对象 / 最近列表”会话状态。

### 5.7 补充：旧业务链路的设备列表也要发 `list`

现象：用户说「7楼得设备」时，曾经有可点设备标签，后来变回纯文本。

根因：这句被 `_scene_followup_pending` 当成场景追问的短补答，跳过了 loop；
场景通道又判定它是 `device_query`，交给旧业务图 `device_query_langgraph`。
旧图只发 `answer`，不发 `list`，前端拿不到结构化设备标签，自然不可点。

修复：

- `graph/device_query_langgraph.py` 的设备列表分支补发 `list` 事件（最多 30 项，`id` 用设备编号，带上 `total`），不论走 loop 还是旧业务图都可点；
- `app.py` 的 `_scene_followup_pending` 不再把「7楼得设备 / 2楼的门禁」当成场景补答（明确带「打开/切到」等场景动作词的除外）；
- 旧业务图发出的 `list` 也写入 `recent_entities`，下一轮「其中一个」可以继续解析。

## 6. UE-FAIL-006：业务追问的楼层回答被场景抢走，且楼层告警本身不被接口支持

### 6.1 对话复现

```
用户：这层楼得安防数据
助手：查询结果：当前没有安防告警事件。不过你说的“这层楼”，我这边没有楼层信息。
      你想查哪一栋、哪一层？告诉我具体楼层后，我再帮你查。

用户：当前层
助手：“当前层”这一点我这边取不到——接口里没有“当前所在楼层”这个上下文。
      请告诉我具体楼层（比如3F、-1F）或区域名称，我再按该范围查。

用户：三楼
助手：已下发动作 scene_switch_floor (floor=3, focus=true)。   ← 本该查 3F 安防，却切了场景

用户：4楼
助手：4楼当前没有安防告警事件。                                 ← 接口不支持楼层过滤，这句话没有数据依据
```

**同类反例（同一会话连续裸楼层）**：

```
用户：总结上周安防事件处理效能
助手：（安防总结）

用户：7漏（7楼）
助手：7楼当前没有安防告警事件。

用户：8楼
助手：8楼当前没有安防告警事件。
```

同一句裸楼层，在上一段对话里被场景抢走，在这里却留在安防域——说明路由结果取决于**隐式历史**，而不是明确的待补状态。

### 6.2 期望

1. 「三楼」是在回答“查哪一层”，应继续查 3F 安防数据，而不是切场景；
2. 如果安防接口不支持按楼层过滤，应明确说明“不支持楼层维度”，不能把园区范围的结果说成 4F；
3. 「这层楼 / 当前层」应使用 UE 当前楼层（前端传入，或后端调用 `get_scene_state`）；
4. 切楼层必须是显式场景指令（「切到三楼」），不能由楼层值本身触发。

### 6.3 根因

**A. 追问是模型自由文本，没有结构化 ask / pending**

- loop L2 的提示词明确写着“缺参数不报错。工具返回‘缺少 X，请问用户’的提示，模型据此发起追问”（[agent/loop/agent.py:18](../agent/loop/agent.py#L18)）；
- `LoopAgent.run` 只返回 `answered / error / aborted / max_steps`，没有 `asked` 状态（[agent/loop/agent.py:276-462](../agent/loop/agent.py#L276-L462)）；
- 所以“你想查哪一层”只是一段 assistant 文本，不是 `ask` 事件，也没有写入 `session_state`；
- app.py 的 `business_waiting` 守卫只认 `session_state` 里的业务追问态（[app.py:2323-2326](../app.py#L2323-L2326)），loop 通道不写这个状态，所以守卫对 loop 无效。
- **刷新页面不会清后端会话**：会话 key 是 `user_id:session_id`，前端刷新后仍复用同一个 `session_id`，`ws_bridge._sessions` 的 TTL 是 1800s（[ws_bridge.py:35](../agent/loop/ws_bridge.py#L35)）。用户以为“新对话”，L2 仍然带着旧历史。要测真正的首轮，必须换一个新的 `session_id`。

**B. 裸楼层值没有明确仲裁：分类是 other，交给 L2 后由历史决定**

日志（2026-11-25 16:34 / 16:43 / 16:52，同一 session）：

```
[classifier] query=三楼, intent=other, score=0.5029, scene_score=0.5823, business_query_score=0.4928
[route] 场景向量兜底，交回旧链路：三楼
[场景分流] query=三楼, business=other(0.5029), scene=0.5823, matched=False, route=True

[classifier] query=7楼, intent=other, score=0.5433, scene_score=0.5929, business_query_score=0.5252
[loop] 提问：7楼        ← 没有交给场景，进了 L2

[classifier] query=8楼, intent=other, score=0.5426, scene_score=0.5942, business_query_score=0.5350
[loop] 提问：8楼        ← 同样进 L2
```

- 「三楼」场景分 0.5823，比业务参照分高 **0.0895**，过了 `SCENE_VECTOR_WEAK_MARGIN=0.08` → 走场景；
- 「7楼」场景分 0.5929，只高 **0.0677**，没过 0.08 → 留在 loop；
- 同一句裸楼层，差 0.02 分就换了通道。分类器给的全是 `other`，**并没有把「7楼」判成安防意图**。
- 进了 L2 后，模型带着同一 session 的历史（前面问过「这层楼得安防数据」），把「7楼」当成安防查询的楼层补充，调用了安防工具——安防工具没有 floor 参数，于是把园区空结果说成「7楼没有」。
- 根因不是“裸楼层 = 安防”，而是**分类器给 other、路由没有明确仲裁，最后由 L2 的历史和模型自由选择工具**。

**C. 业务侧没有当前楼层上下文**

- 聊天请求只带 `query` / `scene_session_id`（[UE场景控制接入说明.md](UE场景控制接入说明.md) §2），没有 `floor`；
- 场景 MCP 有 `get_scene_state`，但业务 / loop 通道不调用它；
- 所以「这层楼 / 当前层」在业务侧真的取不到。

**D. 安防接口本身不支持按楼层过滤**

- `security:getSecurityAlarmList` 入参是 `{}`（[Java-MCP接口清单与Mock返回格式.md:41](Java-MCP接口清单与Mock返回格式.md#L41)）；
- 当前没有按楼层筛选告警的接口/字段；
- 模型把园区范围的空结果说成“4楼当前没有”，属于**用错范围回答**，比直接说“不支持”更危险。

### 6.4 违反的契约

| 契约 | 本次表现 |
|---|---|
| 追问必须是结构化 `ask` + 可恢复状态 | 楼层追问是自由文本，下一轮无法识别为回答 |
| 裸值优先偿还待补问题 | 「三楼」被当成新的场景指令 |
| 参数必须来自本轮或明确上下文 | 「4楼」被当成已过滤楼层，实际没有 |
| 不支持的能力要明说 | 接口不支持的楼层维度被说成“4楼没有告警” |

### 6.5 修复建议

1. **追问结构化**：需要楼层/时间/名称时发 `ask`，并把 `module/missing_params/original_query/done=False` 写入统一会话状态；loop 和旧图走同一套。
2. **路由优先级**：存在待补楼层时，裸楼层值（三楼 / 3F / 3）优先还给等待中的业务域；要切场景必须带“切到 / 切换到 / 展示”等动作词。`business_waiting` 要覆盖 loop 的 `Session.pending`。
3. **当前楼层上下文**：前端在聊天请求里带 `floor` / `build`（或用 `scene_session_id` 调 `get_scene_state`）；「这层楼 / 当前层」直接使用它。
4. **能力守卫**：安防告警工具不支持楼层时，明确回“安防告警接口不支持按楼层筛选，只能按园区/时间；需要楼层维度请确认是否有对应接口”，不要输出“4楼没有”。
5. **文案**：去掉工具名；“已下发动作 scene_switch_floor”这类内部信息只进日志。
6. **会话隔离（前端）**：“清空 / 新对话”轮换 chat session id，并同步场景 WS，或把 `scene_session_id` 与 chat session 分开（后端 `/chat` 已支持 payload 里的 `scene_session_id`）；刷新页面默认保持 session（续聊），不要每次刷新都换 id。注意：换 session 只能清掉旧历史，不能替代第 1–4 条的路由与能力修复。

### 6.6 与前面案例的关系

- UE-FAIL-002：场景追问吞掉业务新指令；
- UE-FAIL-005：业务列表找不到场景里的指代；
- 本条：业务追问的回答被场景吞掉。

三者是同一个“追问态 / 指代态没有跨通道统一记录”的正反两面。

## 7. 是否应该把 LangGraph 改成 loop

**结论：可以迁，但不是本次问题的修复手段；直接迁只会把 bug 一起搬过去。**

理由：

1. **loop 当前显式不接管场景**：`route_plan` 对场景返回 `tool=None` → [pipeline.py:103-110](../agent/loop/pipeline.py#L103-L110) 返回 `handoff` → [ws_bridge.py:208-211](../agent/loop/ws_bridge.py#L208-L211) 返回 `False`，交回旧场景通道。
2. **场景 MCP 的接入约束不同**：`/mcp/scene` 是 direct_client，需要逐请求注入 `X-Session-Id`（[app.py:56](../app.py#L56)）；动作类不能重试；破坏性动作需要显式确认。
3. **loop 同样吃会话历史**：如果把场景工具注册进 loop，LLM 仍会看到上一轮的 `2F`；不补“参数接地 + 能力守卫 + 追问退出口”，问题原样复现。
4. **文档已明确不做**：[loop-agent-TODO.md](loop-agent-TODO.md) T10 “gen_doc / knowledge / scene 纳入 loop：暂不做”；§9 写明原因是“破坏性动作，需要显式确认，走专用通道”。

如果后续确实要统一，前置条件是：

- 把场景工具注册成 loop 的一个业务域，并解决 `X-Session-Id` 注入；
- 破坏性动作走显式确认；
- 动作类超时/不重试策略；
- 合并 `ws_bridge._sessions` 与 `session_state` 两套会话态；
- 在 loop 侧实现同样的追问态退出口和参数接地校验。

这些属于 T18（loop/graph 解耦）之后的架构工作，不适合与本次 bug 修复捆绑。

## 11. 待验证批次：跨通道上下文连续性

> 记录日期：2026-11-25
> 状态：**待验证**。T1 已由截图复现；其余为同一根因推导出的候选用例，尚未逐条执行。

**判定公式**：上一轮产出一批对象（设备 / 候选 / 楼层），下一轮用指代、省略或序号去操作，而两轮被不同通道接走 → 就会掉。

### 11.2 执行方式

1. 先用默认自动分流各跑一遍，记录每轮实际走的通道（日志里的 `[loop]` / `[场景分流]` / `[SCENE FAST PATH]` / `[device_query]`）。
2. 再用 `mode=loop`、`mode=scene` 各强制跑一遍，区分是“通道内丢上下文”还是“跨通道丢上下文”。
3. 每条用例记录：第二轮回答里的名称/楼层是否来自第一轮；日志是否出现 `floor=None, keyword=None`；返回数是否突然变成园区总数。
4. **刷新页面不等于新会话**：前端会复用同一个 `session_id`，后端 loop 历史 TTL 为 1800s。要测“真正无上下文的首轮”，请新建 `session_id` 或等待 TTL 过期，否则 L2 仍会带着旧历史选工具（UE-FAIL-006 的「7楼」就是这样发生的）。

### 11.3 已知限制

- 列表事件最多带 30 个可点标签（`MAX_LIST_ITEMS`），文本最多 60 行（`MAX_ROWS`），所以“第 100 个”一定测不到。
- 自动分流受灰度比例和分类器阈值影响，同一条话术可能这次走 loop、下次走场景；不复现时先确认通道。
- 这些是待验证用例，不是已确认缺陷；确认后的条目再补进第 1–5 节的失败记录。
- 已落地的自动化用例：[tests/test_ue_context_continuity.py](../tests/test_ue_context_continuity.py)。其中 `xfail` 标记的是“修复后应转绿”的需求，未运行，不代表当前已通过。
